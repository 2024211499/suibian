# 乙：首轮实现验证记录

日期：2026-11-28。分支：`feature/server-w2-parse`。本文记录当前实际结果，不表示乙的全部任务完成。

## 已实现

- 现有 `/v1/parse` 在 `MOCK=0` 下执行真实解析流水线；对外仍为 `intent / draft_plan / questions`，无新端点。
- 请求校验、脱敏、模型输出校验、时间规范化、起终点角色核对、地理编码、路线适配和计划图校验。
- 当前首轮接受一个活动、明确的到达或开始时间，以及一种交通方式。多活动、未知或歧义条件返回补充问题；没有伪造完整计划。
- 直接从原话确定支持的相对日期、周几、具体日期和时间含义；模型给错日期不能直接改变计划。支持范围外的时间表达要求用户提供具体日期。
- 明确活动时长写入 `duration`；未明确的活动时长不凭空生成。路程耗时、提前量或混合时长有歧义时返回问题。
- 高德只接入现有 `geocode` 和 `route` 函数，不调用 POI 搜索。支持六种交通方式，公交使用 `citycode` 并避免重复添加等车时间。
- 无法唯一匹配、坐标无效、跨城或城市不一致、无路径、上游错误均停止形成计划。
- 非法 JSON、重复字段、非有限数值、截断与多对象输出被拒绝；重试有界、SDK 隐式重试关闭；取消与程序错误不会包装成上游成功。
- 每个 FastAPI 应用复用模型客户端及熔断状态，关闭时释放连接。
- parse 日额度为 200，可由 `PARSE_LLM_DAILY_MAX` 配置。额度按服务端 UTC 日期统计，不采用客户端时间。SQLite 原子计数支持同机多个进程；存储失效时不调用模型。
- 新增 `STATE_DIR` 和 `PARSE_TIMEOUT_S` 配置。Compose 挂载持久状态卷；当前部署使用一个 worker，使地图的进程内 QPS 限制覆盖整个服务。水平扩容前仍须共享地图限流。

生产代码触点：`server/app/plan_input/`、`llm/`、`gateway/amap.py`、`gateway/cache.py`、`api/routes.py`、`config.py`、`main.py`；部署调整在 `server/Dockerfile` 和 `deploy/docker-compose.yml`。

未修改共用 `schema/`、Android 分支或 `.env.example`。

## 检查中修复的问题

- 旧健康测试把 parse 作为“尚未实现接口”；改为检查仍未实现的 OCR 接口，保留 501 行为覆盖。
- 起终点只做原文子串检查会允许模型颠倒角色，现增加方向语义核对。
- 原实现会遗漏用户说出的“两小时”，现提取明确活动时长或返回追问。
- 无客户端城市时不能采用模型凭空生成的城市编码；要求原文城市依据，并核对地图行政区。
- 原始 JSON 错误不能进入既定重试、底层 SDK 可能隐式多重重试，现按已验证的有限路径处理。

## 尚未验证与当前暂停点

1. `server/.env` 与 `deploy/.env` 当前不存在；未进行真实模型、备用模型或高德调用。需要本地配置后才能验证字段准确率、账户配额、网络和真实地点覆盖率。
2. 用后台进程启动本地服务并执行 curl 的命令被运行策略拦截，工具仅报告 `blocked by policy`，未给出具体原因。该命令未执行；没有启动遗留服务。现有 HTTP 验证通过 FastAPI TestClient 完成，不冒称已通过真实 TCP/curl 实测。
3. `refresh`、和风真实天气、公网部署和甲端真机联调仍属于后续阶段。
4. 首轮仅覆盖单活动计划；多个活动的时间绑定、未知营业/停留信息及更广泛语料需要下一轮完善。
5. Docker 的运行依赖安装尚未切换到锁文件，当前只能声明本地环境已有版本锁定；不能声明容器构建完全可复现。

下一个检查点：配置真实模型与高德，在少量明确输入上核对原话、地点、时间和路线数据；随后再开展下一模块的试点。密钥只放本地环境配置，不进入 Git 或验证报告。
