# 乙：多方案设计与开工决策

日期：2026-11-28。状态：设计比较，未修改公开接口、Schema 或生产实现。

## 1. 明确设计目标

让用户用自然语言建立计划，随后只修改必要信息；时间、地点、交通方式和数据来源得到核实后，才产生可推演计划。一次错误或网络中断不能造成输入丢失、错误覆盖或隐式执行。

三个方案共用同一业务 module：意图理解、时间规范化、地点解析、路线查询、计划组装与验证。interface 对外暴露业务结果，implementation 隐藏模型切换、重试、缓存及配额。不要维护三套独立解析逻辑。

现有 `simulate`、`replan` 和 `PlanGraph` 保持兼容。时间服务使用已讨论的超时与单次重试。GPS、教程和标签的客户端实现仍由甲负责。

## 2. 三种明显不同的方案

### A：无状态解析，客户端持有草稿

**Interface：**保留 `POST /v1/parse`，输入原话与固定 `now`，输出 `intent/draft_plan/questions`。客户端保存原话与已确认回答，每次提交完整有效上下文。若不扩展输入字段，回答只能被规范地合并为文本，这会限制字段级编辑的可靠性。

**使用：**初次解析 → 显示缺项 → 用户选择或补充 → 客户端合并上下文后再次解析。

**不变量：**同一轮时间参照不变；未取得可信路径不交付计划；客户端保存并检查本地请求版本，防止晚到的旧响应覆盖输入。

**隐藏行为：**模型主备、时间处理、地图、缓存、限额和验证都在解析 module 内。第三方依赖通过 adapters 接入，测试替换为已标注的固定数据。

**优点：**公开变动少，部署简单，甲容易继续使用当前客户端。

**代价：**客户端承担上下文管理；补充一个字段也可能重复解析，难以跨请求证明旧确认未被覆盖。不要声称零改动即可得到完整的交互能力。

### B：有版本的规划草稿，字段级编辑

**Interface（新接口提案）：**

- `POST /v1/drafts`：创建草稿并尝试解析。
- `GET /v1/drafts/{id}`：恢复当前草稿快照。
- `PATCH /v1/drafts/{id}`：在 `If-Match` 指定版本上提交经过类型校验的字段修改，返回新快照。

草稿快照包含 `draft_id/version/state/intent/questions/draft_plan`。`state` 区分 `needs_input/ready/unavailable`。常见请求同步返回，先不引入任务队列、SSE 或事件总线。

**使用：**用户说一句话 → 收到版本 1 → 只补一个起点或交通方式 → 收到版本 2。修改交通方式不重新解释日期，只重新查询受影响的路径并重建结果。

**不变量：**写入按版本比较；同版本重试不会创建重复结果；异步外部响应只能提交到它读取的版本；无有效路径不进入 `ready`。用户确认的字段不能被后续模型输出无声覆盖。

**隐藏行为：**字段依赖及失效规则、外部请求去重、版本冲突和计划生成集中在一个 module 中。甲不必拼接对话或理解地图接口。

**存储策略：**甲端持久保存用户原始输入与已确认内容；乙只短期保存脱敏工作副本，建议初始保留 24 小时并设容量上限。若采用现有 Redis，应明确它是短期存储：当前配置没有持久卷且允许淘汰。服务端副本丢失后，以客户端副本创建新草稿并重新验证，不能承诺原草稿 ID 永久可用。

**访问策略：**每份草稿需要独立访问能力，例如随机访问令牌及服务端摘要；设备 ID 只用于限流，不能当作身份认证。HTTP 日志不记录访问令牌和原始输入。

**优点：**最符合渐进填写、缓存恢复和字段级重算；规则和错误处理集中，甲的业务判断更少。

**代价：**需要草稿存储、原子版本更新、重试去重、归属控制、到期恢复和甲端接入测试。旧 `/v1/parse` 保留为兼容入口，复用同一内部解析实现，不同时维护另一套业务逻辑。

### C：类型化交互卡片，客户端按能力渲染

**Interface：**解析结果除了计划状态，返回有限的语义交互卡片；客户端提交卡片答案。卡片只允许预定类型，例如“确认时间”“选择地点”“补充交通方式”，不发送布局代码或任意可执行动作。

**使用：**一句话 → 时间确认卡与地点候选卡 → 用户点选 → 重新评估 → 计划预览。字段已明确时不重复展示卡片。

**不变量：**卡片与草稿版本绑定；旧卡不能修改新版本；客户端不支持的卡片退回文字问题和手动补填，不能把无法展示的问题当成已确认。

**隐藏行为：**何时追问、候选组织、依赖失效和错误引导集中在乙端。甲主要维护小规模、可访问的 Compose 卡片库。

**优点：**交互成本低，地点消歧和时间确认更自然；同一规则可产生一致的界面反馈。

**代价：**两端共同维护卡片协议与兼容性，最容易扩成过大的通用 UI 系统。严格限制为语义问题，不让服务端控制颜色、坐标或任意界面结构。

## 3. 比较与推荐

| 维度 | A 无状态 | B 版本草稿 | C 交互卡片 |
|---|---|---|---|
| 首次接入成本 | 低 | 中 | 中至高 |
| 用户补充一个字段 | 可能重传和重解析 | 字段级编辑与重算 | 直接完成对应卡片 |
| 客户端业务复杂度 | 上下文拼接较多 | 版本和快照为主 | 卡片渲染和能力协商为主 |
| 服务端复杂度 | 最小 | 版本、短期存储、访问控制 | 交互协议与能力兼容 |
| 恢复能力 | 依赖本地草稿 | 本地可靠副本＋服务端短期副本 | 依赖所选草稿策略 |
| 同现有客户端合并 | 最容易 | 保留旧入口，逐步迁移 | 需新的卡片组件 |
| 最适合的用途 | 最快完成兼容交付 | 长期核心设计 | 后续体验增强 |

**推荐 B 作为核心设计，A 作为兼容与降复杂度退路，C 只吸收有限的交互卡片。**这不是同时开发三个系统：一个业务 module，旧入口是一个 adapter，版本草稿是另一个 adapter。卡片只是可选输出投影。

激进目标是从构造过程消除错误：未解析的输入不能冒充计划；每个字段的来源和确认状态可追溯；用户改一个条件，只使相关数据失效；已经确认的条件优先于后续模型猜测。不要仅在输出末尾追加一层 JSON 格式检查。

采用 B 不等于将所有新增想法都列入当前交付。GPS 附近推荐、用户标签和首次教程仍分别与甲协作，不能让其卡住乙的解析、刷新和部署。

## 5. 第一轮试点与验证

先在内部 interface 上用明确标注的固定外部数据验证行为，不调用付费模型或地图；固定数据的结果不能冒充真实联网验收。

| 输入或变化 | 必须观察到的结果 |
|---|---|
| 明确城市、起点、目的地、方式，以及“明早 8 点前到达” | 生成 Schema 与图验证均通过的计划，能进入现有真实推演引擎 |
| 同一草稿仅把骑车改为步行 | 保留日期和已确认地点；仅失效并重查相应路线，版本前进 |
| 只说“周三 8 点”，存在周别或时间用途歧义 | 保留已识别字段，返回有针对性的补充问题，不生成伪完整计划 |
| 地点或路线不可用 | 保留草稿及明确原因，不出现编造坐标、零耗时或可执行状态 |
| 旧请求晚返回或同一编辑重试 | 不覆盖新版本、不重复计费请求；并发去重效果需要显式实现和测试 |
| 模型输出违反业务结构、重试仍失败 | 在预算内失败或切换备用服务，最终输出可处理的业务失败，不抛原始异常给甲 |
| 退出恢复或跨午夜继续补充 | 原输入与已确认日期可恢复；过期数据重核，不偷偷平移日期 |

测试先用实际业务结构，不能只证明一个 `count` 字段可解析。首轮试点通过后再决定是否需要新增公开 Schema；任何新增 Schema 都提交具体差异和请求响应样例供确认。

## 6. 已发现、应在实现中处理的问题

- Docker 当前开启两个服务进程，进程内日计数不能保证全局额度；上线限额需要共享原子存储或明确单进程限制。
- 当前 Redis 无持久卷且使用 `allkeys-lru`；日配额计数也不能因内存淘汰而复位。缓存淘汰与限额存储策略必须分清。
- Docker 构建尚未使用新依赖锁定文件；目前锁定只覆盖本地环境，还不能声称容器构建可复现。
- 现有 smoke 脚本输入只有“三教”，没有明确城市和起点；可靠解析不应为了让旧 smoke 变绿而猜地点，后续应改用完整、已核实的验收输入。
- 现有提示词与意图 Schema 在时间字段上的表达不一致；需要按正式解析输出整理，不能让提示词继续要求 Schema 不允许的字段。

这些问题已具备可实施解法，不是继续无限前期设计的理由。离线试点无需等待凭据、服务器或界面全部齐备。
