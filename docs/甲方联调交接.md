## 2. 甲端接入顺序

1. 将 Retrofit Base URL 配为上表的 HTTPS 地址，保留末尾 `/`；接口相对路径统一写 `v1/...`，避免拼成 `/v1/v1/...`。
2. 接入注册/登录，并给业务请求加 Bearer 请求头。启动恢复会话时可调用 `/v1/auth/me` 检查令牌。
3. 先打通单活动 `parse → 本地保存 → simulate`，再接 `refresh` 和 `replan`。
4. 将 `draft_plan`、天气推演的 `sim`、`depart_by`、到达时间等可空字段正确处理，未知信息不能显示成零。
5. 同一计划的旧请求如果晚返回，不能覆盖用户已经编辑的新计划。应用响应前核对发起请求时的 `plan_id/version` 及当前本地状态。

接入 HTTP 客户端时，建议连接超时 10 秒、读取超时 40 秒、整次调用超时 45 秒；这是客户端建议值，不是服务端延迟保证。旧 8 秒读取超时容易中断真实解析或天气推演。提供加载与取消入口；不要自动连发重试，避免消耗重复额度。短暂网络重试保留原请求的 `now`，用户修改后发起新请求时重新取时。

## 3. 注册、登录与令牌

| 请求 | 请求体/要求 | 成功结果 |
|---|---|---|
| `POST /v1/auth/register` | `username`、`password` | 201，并直接返回登录会话 |
| `POST /v1/auth/login` | 同上 | 200，返回登录会话 |
| `GET /v1/auth/me` | Bearer 令牌 | 200，返回 `id/username/role` |
| `POST /v1/auth/logout` | Bearer 令牌 | 204，**没有 JSON 响应体** |
| `GET /v1/health` | 无须登录 | 健康与配置情况 |
| `GET /v1/version` | 无须登录 | 版本信息；当前 `apk_url=null`，没有自动下载 APK 能力 |

请求示例仅表示字段；用户名和密码由用户自己填写，不把示例作为公共账号：

```json
{"username":"your-username","password":"your-own-password"}
```

用户名为 3–32 位英文字母、数字或 `_.-`，统一转小写，不区分大小写；密码 12–128 字符。注册不能提交 `role`。

会话返回结构：

```json
{
  "access_token": "服务器生成的令牌",
  "token_type": "bearer",
  "expires_in": 86400,
  "user": {"id": "用户ID", "username": "your-username", "role": "user"}
}
```

令牌有效期 24 小时，没有 refresh-token 接口；过期后重新登录。退出只撤销当前令牌。甲端在应用私有存储中保存令牌，不把密码、令牌或 Authorization 写进日志。退出/换号时清除旧会话，按账号隔离本地计划，避免把上一人的数据展示给下一人。

鉴权拦截器处理 401 时引导登录，不无限重放请求。不要把 `AUTH_REQUIRED=0` 当成正式接入办法。管理员角色用于配置团队供应商凭据，普通用户页面不需要管理员入口；详细管理员接口见[账号与团队凭据联调](乙_账号与团队凭据联调.md)。

## 4. 一句话录入 `/v1/parse`

`POST /v1/parse`，请求 JSON：

```json
{
  "text": "明天上午十点前到中国国家博物馆参观，从天安门出发，步行。",
  "now": "2026-11-28T21:00:00+08:00",
  "city_adcode": "110100"
}
```

这是明确单活动的联调示例；发送时替换 `now` 为当前系统时间并带时区。`city_adcode` 是六位行政区划编码，不是电话区号。不要在产品里固定示例时间、城市或地点。未提供城市时可能收到补充问题。`text` 长度 1–4000，空白文本、无时区/格式错误时间会返回 422。

成功及可恢复失败统一使用原有三个顶层字段：

```json
{"intent": {}, "draft_plan": null, "questions": ["请补充并确认从哪里出发。"]}
```

上面是**顶层形状示意**，实际 `intent` 含完整意图字段。处理分两种：

- `draft_plan` 为对象且 `questions=[]`：展示草案，用户确认后本地保存；使用返回的完整计划对象进入推演。
- `draft_plan=null`：展示 `questions`，保留已输入内容和 `intent`；不允许保存为可执行计划、继续推演或部署。模型/地图失败、额度用完、超时也可能走这个 200 响应，不是只有非 200 才算失败。

没有独立草稿会话或追问接口。用户补充后，客户端把**原安排和本次补充**组成新 `text`，重新请求 `/v1/parse`；不要只发“8点”这类孤立答案。保留原文供用户编辑，避免反复重输整句话。

当前真实录入可交付的是明确的**同城、单日、单活动**。跨国航班、条件分支、多活动方案不会自动执行。例如用户提供的“见导演，谈成坐飞机，没谈成再见另一人”应保留条件和时刻，提示补充/范围限制并返回空草案；模型没有航班查询或跨时区行程执行能力。

## 5. 推演 `/v1/simulate`

`POST /v1/simulate`。以下为请求构造伪代码；`P` 表示上一步返回并经用户确认的**完整计划对象**，不是字符串或只含 ID 的对象：

```javascript
const body = { plan: P, depart_min: 450, n: 2000, seed: 42 };
```

`depart_min` 是**计划当天零点起的分钟数**，450 表示 07:30，范围 `0 <= depart_min < 1440`。它不是时间戳、旅途分钟数，也不能用设备当前时刻代替未来计划的出发时刻。`n` 可选，范围 1–2000，默认 2000；`seed` 可选，固定值便于联调复现。

响应包含 `sim`、`evidence`。甲端需要读取：

| 字段 | 含义/处理 |
|---|---|
| `sim.p_all` | 整体满足约束的估计概率，0–1；显示百分数时乘 100 |
| `sim.per_node` | **数组**；每项含节点 ID 与该节点结果，不是以节点 ID 为键的对象 |
| `sim.per_node[].arrive_p90` | 真实引擎返回浮点数或 `null`，单位是计划当天零点起的分钟数；可能超过 1440，需要按天进位 |
| `sim.per_node[].slack_p50` | 余量分钟数或 `null`，可以为负数；不能当作时分字符串 |
| `sim.weakest` | 最薄弱节点信息；按实际返回处理可空值 |
| `sim.depart_by` | 建议最晚出发时刻；`null` 表示没有找到满足目标的出发时刻，不能填默认时间 |
| `evidence.labels` | 数值来源；保留并用于来源说明 |

空图、悬空边、缺少 `depart_min` 等会被拒绝。只传 `{plan_id: ...}` 不符合真实接口契约。服务端不按 ID 读取用户保存的计划。

**真实引擎与旧 mock 示例有一处必须注意的差异：**旧 `schema/examples/simulate.json` 把 `arrive_p90` 写成 `"07:52"`，真实引擎返回分钟数。真联调 DTO 应支持数值/空值，例如 Kotlin `Double?`，显示时再换算为时分；若同时保留旧 mock 模式，需要在解析边界兼容旧字符串。`depart_by` 则仍是时分字符串/空值，不能把两个字段共用同一类型。

日期理解也需要区分“能保留原词”和“能生成计划”：“昨天”等过去时间会要求用户确认；“次日/翌日/第二天”目前需要前文明确日期，否则追问具体日期。不得在客户端把这些情况偷偷改为今天或明天。

默认推演不请求天气。启用天气时仍是同一端点，额外传：

```javascript
const body = { plan: P, depart_min: 450, n: 2000, seed: 42,
               use_weather: true, now: currentTimeWithOffset };
```

天气模式要求 `P.date` 和路段起点坐标有效；出发时刻应为尚未过去的计划时刻。如果当前时间含秒，不能把当前分钟的分钟数当作未来时刻。`now` 的时区应与计划当地时区一致；本轮按同城单日使用。

| 天气推演结果 | 甲端处理 |
|---|---|
| `weather.status=applied` 且 `sim` 有值 | 展示天气情境下的结果及来源 |
| `weather.status=blocked` | 检查 `blocked_edges`，提示改时间/方式；不能自动替用户执行 |
| `weather.status=partial/unavailable`、`sim=null` | 明确显示天气资料不足，不伪造完整概率；用户可刷新，或明确选择普通推演 |
| 节点到达时间/余量为 `null` | 显示未知/不可达，不能显示 00:00 或 0 分钟 |

天气修正由服务端计算，不要先在客户端给 ETA 加雨天系数，再调用天气推演；这会重复修正。天气采用每条路段起点的小时预报近似，并非沿途精确天气或到达保证。

## 6. 天气与路线刷新 `/v1/refresh`

`POST /v1/refresh`：

```javascript
const body = { plan: P, now: currentTimeWithOffset };
```

完整计划需要至少一条路段，并且每个地点都有有效坐标。返回：`plan_patch`、`changed`、`weather`、`errors`。

**`plan_patch.edges` 是按边 ID 合并的局部更新，不能拿它替换整个 `P`，也不能把未返回的边删掉。** 处理顺序：

1. 确认响应对应的仍是发起请求时那份计划；用户已编辑或切换计划时丢弃过期响应。
2. 将 `plan_patch.edges` 中每一项按 `id` 合并到已有边，保留其余节点、边和字段。未返回的边保留旧值，并提示该项刷新失败。
3. `changed` 是数值发生改变的边 ID，不等于所有刷新成功的边。即使 `changed=[]`，返回的来源取数时间仍可能需要更新。
4. 清除与旧输入绑定的推演结果，再对更新后的完整计划调用 `/v1/simulate`。刷新接口不会保存计划、递增版本或替你重算概率；本地数据变更和版本管理由甲端负责。

`weather` 用于展示当前预报与可用性，`errors` 可包含单个天气源或路线失败。HTTP 200 不代表所有项刷新成功。

| 字段 | 解释 |
|---|---|
| `weather.status` | `ok`、`partial` 或 `unavailable`；部分失败仍保留成功资料 |
| `weather.bike_available` | `true/false/null`；`null` 是未知，不能视作可以骑行 |
| `weather.hourly_precip_mm` | 小时降水量；`null` 与 0 必须区分 |
| `weather.precip_from_at` | 含日期和时区的降水开始预报；`precip_from` 为展示用时分 |
| `weather.warnings` | 可用预警；源不可用时空列表不等于已确认无预警，需一起看状态及错误 |
| `weather.attributions` | 来源署名；展示天气资料时保留 |
| `weather.effects_source` | `default` 表示规则估计，不能包装成地图实测耗时 |

`refresh` 的天气范围是计划起点；不要将起点天气宣传为整段旅途的逐点天气。`precip_from=null` 也不单独表示全程无雨，需结合分钟预报来源是否可用及预报覆盖范围。

## 7. 重排 `/v1/replan`

`POST /v1/replan`，以联调中人为模拟 15 分钟延误为例：

```javascript
const body = { plan: P, depart_min: 450, n: 2000, seed: 42,
               trigger: { kind: "weather", data: { edge_id: P.edges[0].id, delay_min: 15 } } };
```

`kind` 仅支持 `weather`、`route_delay`；`delay_min` 大于 0，最大 1440。这两个类型当前均把调用方提供的延误加到指定边再复算，**`kind=weather` 不会自动查询降雨，也不会自动推导 15 分钟延误**。联调按钮应明确标“模拟延误”，不能称作实时观测。

响应包含 `base_version`、`before`、`after`、`affected`、`options`、`relax`。当前可提供的是 `keep_route`：

- `options` 可能为空，表示没有可交付的保留原路线方案；不要把 `after` 当成已经获得可执行替代方案。
- 非空项的 `plan_after` 是完整新计划，版本为原版本 +1；用户确认后才替换本地计划。
- 应用前再次检查 `base_version` 与请求时的计划版本，避免旧重排覆盖新编辑。
- 当前没有自动换交通方式、替换景点、航班查询或自动执行日历/导航。天气重排后如需验证真实天气，要对新计划再调用天气推演。

## 8. 失败、额度与资料保留

| 情况 | 甲端行为 |
|---|---|
| 网络失败/超时 | 保留原文和本地计划，结束加载并允许重试；不显示假成功 |
| 401 | 令牌无效或过期，引导重新登录 |
| 403 | 权限不足；普通用户不能调管理员配置 |
| 409 | 注册用户名占用；本轮没有同步版本冲突接口 |
| 422 | 输入/计划无效；`detail` 可能是字符串或校验列表，兼容两种显示 |
| 429 | 认证或管理员请求过频，按 `Retry-After` 等待；不要循环重试 |
| 503 | 服务配置等暂不可用，保留输入并通知乙方检查；错误正文不写入含凭据日志 |
| parse 200 + 空草案 | 按 `questions` 引导补充或等待恢复；额度不足也通过此路径表示 |
| refresh 200 + `errors` | 展示部分成功/失败，保存成功更新但保留失败项的旧资料和过期提示 |

当前解析上限：全局每日 200 次、每用户每日 50 次；按服务端 UTC 日期计数。注册/登录有限流，联调复用测试账号，不要循环注册。切勿在 App 启动或定时任务中反复调用真实解析、管理员测试来“探活”；探活用 `/v1/health`。

## 9. 双方联合验收清单

先完成最小链路，再做异常场景；每项记录设备、时间、请求结果和必要的脱敏截图。

- [ ] 健康接口正常；手机使用 HTTPS Base URL 能访问。
- [ ] 注册/登录、恢复登录态、401 重登录、退出 204 均正常；没有凭据日志。
- [ ] 明确单活动输入返回真实坐标、路线来源及完整草案；确认后本地保存，重开应用能读回。
- [ ] 缺起点或时刻时展示问题，保留原文，补充后可再次解析；空草案不能进入执行。
- [ ] 完整计划调用推演，概率、节点结果和最晚出发时间正确展示；缺少必要参数返回 422。
- [ ] 刷新按边 ID 合并；部分天气失败、未知骑行状态和过期来源不会被显示成正常天气。
- [ ] 模拟 15 分钟延误后，展示前后影响；仅在用户确认后采用 `plan_after`，空方案有明确提示。
- [ ] 离线、切换计划、连续修改与迟到响应不会丢本地数据或覆盖新编辑。
- [ ] Android 自身日历、通知、闹钟、后台及权限逻辑由甲验证；至少一台 ColorOS 真机，服务端 CI 不能替代真机结果。

Android 端构建 APK 后安装测试；保持乙方电脑、后端和隧道运行。临时域名依赖 cloudflared 进程，重开隧道可能换地址；**只重启后端、保留隧道时无须更换当前 Base URL**。

## 10. 服务状态与维护

本机后端监听 `0.0.0.0:8000`。本次交接核对中，公网健康接口返回 `status=ok`、`checks.schema=ok`、`checks.config=ok`；运行进程启动时间为 2026-11-28 21:13（UTC+8），晚于业务提交 `96eecc7`。这确认先前的旧进程已更换；不是新一轮真实供应商全链路证明。历史运行 PID 记录可能过期，维护时检查实际端口，不依赖旧 PID。

乙在自己的后端终端按 `Ctrl+C` 停止后，从仓库根启动：

```powershell
Set-Location 'G:\temp\suibian\suibian-main\server'
..\.venv\Scripts\python.exe -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1 --no-proxy-headers --no-access-log
```

保持该窗口和 cloudflared 隧道运行。维护期间先与甲约定短暂停测；启动后核对 `/v1/health`。甲只接远程 API 时无须在自己的电脑启动 Python 服务。

自动冒烟可在仓库根执行，已有账户登录，密码隐藏输入：

```powershell
.\.venv\Scripts\python.exe scripts/deploy_smoke.py https://heritage-skins-ticket-civil.trycloudflare.com --login --parse-file request.json
```

`request.json` 使用第 4 节结构并填当前 `now`。不传 `--parse-file` 只验基础推演，不能据此宣称解析已验收；`--allow-mock` 只用于开发镜像检查，不能替代真实调用。
