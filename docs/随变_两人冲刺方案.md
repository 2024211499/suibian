## 〇 容量账：为什么全量 P0 两个人可行

1. **工作量结构对了。** 原方案 4 人的活里，界面、CRUD、接口适配、文档占大头——正是 AI 辅助效率最高的部分。人只保留四类不可外包的工作：架构与 schema 决定、引擎逻辑审读、测试编写与执行、真机验证。
2. **排期按依赖序，不是按功能清单序。** 引擎（推演/搜索/画像）先立起来，生成流水线大部分复用引擎（v2 4.9：生成 = 排程器 + 已有的推演打分），排 W4；应变闭环 W3 成型后，生成只是"从空白排一张计划图"，不是新系统。
3. **三处诚实简化（不减少功能，只降低实现深度）：**
   - 到达观测只用"点'到了' + 复盘补填"两条来源——定位本来就是 v2 的 P1（3.5），不是砍；
   - 待订清单只做"确认页 + 跳转"，不解析任何订单接口，页面明写"不代订、不填表"；
   - 微信草稿走"复制 + 打开微信"——v2 5.2 的退路即正路，不接微信 SDK。
4. **滑周了按第八节的压缩次序降实现深度/顺延，不砍功能。**

## 二 四个阶段的实现细化

### 2.1 生成（1.7 + 2.1 + 2.2）

**大模型输出的另外两份 Schema（W1 周三和 plan_graph 一起冻结）：**

`intent.schema.json`：

```json
{
  "city": "杭州", "city_adcode": "330100",
  "date": "2026-12-05", "date_fuzzy": "本周六",
  "origin": {"text": "家", "resolved": false},
  "return_by": "18:00", "return_by_fuzzy": null,
  "members": ["我", "小王", "小李"],
  "budget_yuan": null, "budget_tendency": "normal",
  "must":  [{"text": "看个展", "category": "exhibit"}],
  "prefs": [{"text": "想吃本帮菜", "category": "meal", "keyword": "本帮菜"},
            {"text": "别太累", "constraint": "walk_total_km_max", "value": 8}],
  "questions": ["几点要回到家？"],
  "unsupported": []
}
```

- `questions[]` 装关键缺失项（几点到家/几个人/预算），手机追问一轮后继续；`unsupported` 装跨城、多天、>6 站，前端据此提示"目前只支持一城一天"并引导 1.1。

`skeleton.schema.json`：

```json
{"slots": [
  {"slot_id": "s0", "category": "hub",     "keyword": "去程交通", "hard": true,  "value": 5, "after": []},
  {"slot_id": "s1", "category": "sight",   "keyword": "",         "hard": false, "value": 3, "after": ["s0"]},
  {"slot_id": "s2", "category": "meal",    "keyword": "本帮菜",   "hard": false, "value": 3, "after": ["s1"]},
  {"slot_id": "s3", "category": "exhibit", "keyword": "",         "hard": false, "value": 3, "after": ["s2"]},
  {"slot_id": "s4", "category": "hub",     "keyword": "返程交通", "hard": true,  "value": 5, "after": ["s3"]}
]}
```

- `keyword` 为空 = 用 `defaults.yaml` 的类别默认词（sight→"景点"、exhibit→"展览馆"…）。
- **Schema 里没有时间字段、没有地名字段**——骨架阶段"不出地名不出时间"是结构保证，不靠提示词自觉。

**流水线六步**：参数照技术文档第四节表（时限合计 20 秒，超时用已有结果出 `partial`）。两点修正：
- 详情接口（`/v5/place/detail`）属于**基础搜索服务**配额：一次生成搜索类调用 = 搜索 6 + 详情 3 = **9 次**；
- `/v3/distance` 按"不同终点数"计次，精排的真实距离矩阵约 **8–10 次**（原表写 3 次是错的），一次生成总调用 ≈ 34 次。

**三套挑选**（技术文档 4.3）：稳妥/紧凑/省钱 + 门槛（紧凑省钱要 p_all ≥ 0.8），不够三套时如实显示"只找到两套有把握的安排"。

**页面**：生成进度页接 SSE（事件序列照技术文档 3.1），方案先出先显示；三卡对比（把握、出门时间、花费、步行距离、最薄弱环节）；选中 → 变成普通 DRAFT 计划图，**和 1.1 录入走完全相同的后续流程**——这是"同一引擎跟到结束"的代码体现。

**验收：** 15 句生成测试集 ≥13 句 20 秒内出 ≥2 套；每套地点真实存在、营业时间内到达、硬约束满足（`run_generate.py` 自动检查）。

### 2.2 部署（1.8 + 出门提醒公式）

- 选定计划 → `DeployPlanUseCase` 组装动作清单：每节点 1 条日历（一批一次确认，一次授权）+ 出门闹钟 + T−2h 闹钟 + 待订清单，全部挂同一个 `batch_id`，操作日志可整批撤销。
- **出门提醒时刻公式（这次写死进代码和文档）：** `remind_at = depart_by − prep.mu`。`depart_by` 来自推演二分（目标把握默认 90%）；`prep.mu` 初值 = 冷启动问答"说 5 分钟出门实际要多久"的答案，没答就是 10 分钟；复盘后自动更新。出门闹钟用 `setAlarmClock()`（Doze 准点）。
- 待订清单 = 计划图里 `order.type ≠ null` 或 `category ∈ {train, flight}` 的节点 → 清单项 {名称、时间、跳转方式}，按 `jump_only` 级跳转（高德/12306 网页或 App 搜索页），**不代订、不填表**。
- 部署确认页一屏列全：将写几条日历、设哪两个闹钟、有哪些待订项——一个"确认部署"按钮。

### 2.3 应变（3.x + 4.x + 5.x）

- **感知**：tick 调度照技术文档 8.3 的表（T−12h / T−2h–30m / 30m–出发 / 途中）；Doze 下 5 分钟会变 9 分钟，验收线 ≥60% 触达（W1 spike 决定参数）。
- **两条入口汇到同一条管线**：tick 发现风险、用户一句话报告（`/v1/report`，"小王晚 25 分钟"→ 事件）→ `/v1/replan`：
  1. 变化写进计划图副本；
  2. 重推演 → **影响列表** = {p_ok 变化 > 5 个百分点，或 slack 转负的节点}——"影响到哪几步"的答案；
  3. 算子搜索（技术文档 7.3，5 算子 + Pareto + 主算子多样性）→ 三张方案卡。
- **方案卡一屏结构**：发生了什么（一句话 + 依据面板入口）/ 影响 2–3 行（节点名 + 把握前后对比）/ 方案 2–3 张（主算子、新把握、代价明细、需要的动作）/ "先不改"。
- **确认执行**：选卡 → 手机本地组装动作列表（服务端只有算子，没有动作）→ ActionGateway 六步（12.2）→ 同 batch 整批撤销。
- INFEASIBLE：P0 文案"××最多只有 y% 把握"+ 把握最高的方案；最小放宽集（7.4）P1，W6 有富力再做。

### 2.4 复盘（6.x + 回灌）

- 复盘三问顺序照技术文档 8.5（异常观测 → 缺到达时间的节点 → 方案有没有用），最多 3 问。
- 提交后手机端跑 `BayesUpdater`（7.5，Kotlin），复盘卡底部用固定模板显示变化："你步行|高峰比导航慢 12%，下次会提前 4 分钟提醒你"。
- **回灌生成**：步行系数高 → 粗排少排步行段（4.2 的方式选择规则读画像）；"别太累"类软约束记进 `choice` 表。这就是"下次生成的计划更贴合你的节奏"的落点，也是演示视频的收尾镜头。
- 画像页：逐项显示 mu / 基于几次 / 可信区间，可改、可重置、可暂停学习。

### 2.5 贯穿件

- **可信可控 7.1–7.5**：`actions.yaml` 唯一来源 → Gradle 生成 Kotlin 枚举；ActionGateway 六步流程；授权中心；操作日志；`forbidden_scan.sh` 进 CI（12.3）。这组约 2 天工作量，是答辩硬通货，排 W3–W4 不许挪。
- **回放演示模式**（一份格式三处用：视频兜底/答辩断网兜底/离线评测）：`assets/demo/{sample_id}/events.jsonl`（`{t_offset_s, api, request, response}` 每行一条），OkHttp 拦截器按 `t_offset` 回放，间隔压缩 0.3；回放模式下依据面板顶部和角落固定"演示数据"水印。debug 构建的录制开关从 W2 就加上，边开发边攒素材。
- **H5 同行人页**（v2 P1）：W6 有富力才做，按技术文档第十一节；演示视频不依赖它（S2 用草稿闭环）。

## 四 AI 辅助工作法（这是"两个人干四个人的活"的前提）

**任务单模板**（每次给 AI 的输入固定四样）：

```
1. 目标文件清单（只做这一个模块）
2. 依据：技术文档第 X 节 + schema/ 下相关 JSON
3. 先写测试：13.1 表中对应行（人先看测试对不对，再让 AI 写实现）
4. 禁止：写死模型名/密钥/城市名；调用 12.3 禁用接口；生成数字进文案
```

**完成定义**：单测绿 + CI 绿 + 真机演示过。说"完成"必须贴测试命令和输出（技术文档第十五节的规矩照旧）。

**分工细则**：
- 甲的 AI 任务：页面、ViewModel、Room DAO、执行器、Retrofit/SSE 客户端。甲亲自写：`PlanStateMachine`、`ActionGateway`、`BayesUpdater`。
- 乙的 AI 任务：网关适配器、CRUD、提示词初稿、评测脚手架。乙亲自写：`simulate`、`search`、`depart_by`、生成排程器，并逐行看懂。
- 每周六互审 1 小时：甲审引擎测试，乙审状态机/关卡测试（防关键人风险）。
- 提示词改动必须重跑 `run_generate.py`，结构合法率不得下降（5.3）。

| 回放评测 | 30 条（≥10 条真实），影响识别 F1、方案可行率 | 影响识别对照纯大模型 |
| 概率校准 | Brier + 校准 10 档 | `fixed_rule.py`（提前 N 分钟，N=10/15/20） |
| 操作成本 | 4–6 人 × 2 任务，手动 vs 随变录屏计时 | — |
| 试用 | 5–8 人 × ≥5 天 + 访谈 3–5 人，埋点导出 JSON | 计划书如实写人数 |

## 七 配额与成本（月配额版）

高德个人认证月配额：基础 LBS（路径/距离/地理编码）**15 万次/月**；**基础搜索（关键词/周边/ID/输入提示）5000 次/月**。参数：

| 项 | 参数 |
|---|---|
| 缓存 TTL | POI 30 天、地理编码 30 天、路径 10 分钟（15 分钟时段键）、天气照 2.6 |
| 搜索日预算 | `rl:search_daily` 上限 120 次/天；超了 parse 只做地理编码、`swap_place` 停用 |
| 生成上限 | `DAILY_GENERATE_MAX=10`（每次 ≈9 次搜索类 + 8–10 次距离 + ≤15 次路径） |
| 月耗估算 | 试用 8 人：搜索 ≈ 8 人×1 生成/天×9 + 录入重排 ≈ 120/天 ≈ 3 600/月 + 预热 500 ≈ **4 100 < 5 000 ✓**（紧，充 ¥30 搜索流量包兜底） |
| 预热 | 学校周边 3 km + 杭州西湖周边（W1 就跑） |
| 手机端 | 不做输入提示（耗搜索配额） |

总成本：域名 ¥30–80 + 香港服务器 ¥200–400 + LLM 几十元 + 流量包 ¥30 ≈ **¥600 以内**。
