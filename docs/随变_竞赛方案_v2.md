# 随变：让日常计划经得起变化的系统级智能体

> 第二十届全国大学生软件创新大赛 · 赛题2「AI 融入日常」· 竞赛方案 v2
> 本版依据：附件1《赛题详情》原文。不再依赖新闻、统计数据和春运场景。

## 〇 这一版改了什么

| 上一版的问题 | 这一版的做法 |
|---|---|
| 主线是春运和火车晚点，场景窄，真实验证要等寒假 | 主线改成"任何有时间、地点、人和订单的计划"：赶课、赴约、朋友聚会、周末短途。火车、飞机只是其中一种出行方式 |
| 堆了很多现实调研（新闻、统计、竞品细节） | 全部删掉。每一部分只回答一个问题：对应赛题哪句话、评委怎么打分、我们怎么做出来 |
| 有几项功能只对铁路有用，而且难做（GPS 推算列车位置、权益助手、防诈） | 删掉。换成赛题原文点名的能力：多人协调、从聊天和截图整理信息、耳机和手表交互 |
| 算法名词多，讲不清 | 核心技术收敛成一个引擎：**计划图 + 变化推演 + 方案搜索 + 画像**，每一步都写清输入、输出和实现方法 |
| 只能处理用户已有的计划，闭环的起点要靠用户自己排好 | 新增**一句话生成计划**：说一句话，得到 2–3 套算过把握的可选计划，选一套后一键部署到日历和提醒。生成和应变用的是同一个引擎（见 4.9） |

**结论先说：选题不用换，但定位要从"出行应变"升级成"日常计划应变"。** 功能不再横向加大类，而是把一条闭环做深、做实：一句话出计划 → 选一套部署 → 变了接着改 → 结束后复盘、更新画像。原因见第一节。

## 一 选题判断：为什么还是「随变」

### 1.1 赛题2原文几乎就是在描述这个作品

| 赛题2原文 | 随变对应的能力 |
|---|---|
| "完成一件普通的事情，往往需要反复查找信息、比较选项、协调他人和**应对变化**" | 四件事全覆盖：一句话生成计划替用户"查找信息"，2–3 套计划并排"比较选项"，聚会 H5 "协调他人"，重点做"应对变化"，这是现有 App 最弱的一环 |
| 核心问题："理解情境、连接服务并**处理变化**" | 计划图理解情境；地图、天气、日历、消息是连接的服务；变化推演和方案搜索负责处理变化 |
| 例子："组织朋友聚会需要确认时间、选择地点、规划路线并通知成员" | 场景 S2 聚会，完整实现 |
| 例子："周末短途旅行，涉及交通、住宿、天气、订单和临时调整" | 场景 S3 短途，完整实现 |
| 日常通勤方向："当行程变化时，也可协助调整后续安排、提醒同行者或提供替代方案" | 场景 S1 赶课/通勤，原文三个动作一一实现 |
| 短途方向："当计划发生变化时，AI 可帮助分析影响、提供替代选择并协助同步信息" | 连锁影响推演、方案卡、同行人同步 |
| "还可发挥耳机、手表等设备的特点，让用户在步行、骑行或携带行李时，减少对手机的频繁操作" | 耳机播报加语音确认，手表一键确认 |
| "涉及支付、退订和个人信息共享等操作时，应由用户明确确认" | 动作分级表：这类动作只跳转、不代办 |
| 场景清单："日常通勤、周末游玩、短途旅行、多人同行和突发情况处理" | 三个主场景加多人模式，覆盖清单中的五项 |

### 1.2 换成日常计划后，四个好处

1. **持续使用价值变高。** 火车一年坐几次，赶课和赴约每周都有。评审第六项"持续使用和拓展复用"直接受益。
2. **真实验证随时能做。** 不用等寒假，同学每天都能用，初赛前就能拿到两周的真实数据。
3. **跨应用、跨设备、跨场景更自然。** 一个计划同时牵扯日历、地图、天气、聊天、订单、同行人，系统级协同是刚需，不是硬凑。
4. **技术核心不变。** 计划图、概率推演、方案搜索、画像这套引擎对所有场景通用，换场景只是换"场景模板"。

### 1.3 一句话定位

> **一句话出计划，变了也不慌。**
> 你说一句"周六和小王小李去杭州玩一天"，别的 AI 给你一篇攻略；随变给你两三套算过把握、标出最薄弱环节的计划，你选一套，它帮你写进日历、设好出门提醒、列出要订的位。出发后它盯着天气、路况、消息和同行人，一有变化，先算清楚影响到哪几步、还有多大把握，再给出两三个可比较的方案；你点头，它才去调导航、改日历、起草通知。结束后复盘，更新你的画像，下次生成的计划更贴合你的节奏。

这句定位里的每一步都对应一个阶段：**生成 → 部署 → 应变 → 复盘**，见 2.3。"一句话出计划"本身不新，新的是生成的计划从第一秒就带着概率和预案，并且同一个引擎一直跟到计划结束。

## 二 产品定义

### 2.1 做什么、不做什么

| 做 | 不做（以及原因） |
|---|---|
| 一句话生成 2–3 套可比较的计划，每套标把握和最薄弱环节；也能导入、体检已有的计划 | 不做长篇旅游攻略和景点种草。只排时间、地点、路线和订单，单个计划限一天内 3–6 站，所有时间和路程都来自地图接口，不让大模型编 |
| 变化发生时算影响、给方案、协助执行 | 不做全自动代办。支付、退订、发消息必须由人确认，这是赛题硬要求 |
| 多人计划的时间协调、信息同步 | 不做聊天软件。通知走用户自己的短信或微信，随变只起草 |
| 从个人历史中学习时间习惯和取舍偏好 | 不做全天候监控。只在有计划的时间段工作，可随时暂停 |

### 2.2 三个代表场景

三个场景从"每天都有"到"一月几次"，覆盖个人、多人、多环节三种复杂度。

**S1 赶课与通勤（个人 · 每天）**
小林周三早上 8:00 在东区有课，平时 7:30 出门骑车。7:05 随变发现 7:20 起有中雨，骑车不现实，公交要 28 分钟。它在 7:08 推送："建议 7:22 出门坐公交，赶上概率 93%；如果 7:30 出门只有 41%。"小林在手表上点"好"。7:40 公交堵车，随变重算后发现会晚到 6 分钟，于是起草一条给小组同学的消息："路上堵车，预计晚 5 分钟，签到帮我留意一下"，小林确认后发出。

**S2 朋友聚会（多人 · 每周）**
小林对随变说"周五晚上约 4 个朋友吃个火锅"。随变生成一个 H5 链接发到群里，朋友不用装 App，点开填可用时间和出发地点。随变算出共同时段 18:30–21:00，按"最远那个人的路程尽量短"挑出 3 家候选餐厅，每家标出各人路程和"全员准时到"的把握，大家投票。定下后，随变把聚会写进小林的日历，给每人生成出发提醒，并列出"订位"这一步让小林自己点进去订。周五 18:10，小王说"临时加班，要 19:20 才能到"。随变推演：等他就超过餐厅保留时间，不等他就少一个人。它给出三个方案：推迟到 19:30 并起草给餐厅的改时消息；先到的人先吃；换一家离小王近的店。小林选第一个，随变同步新时间到所有人的 H5 页面。

**S3 周末短途（多环节 · 每月）**
小林说："周六和小王小李去杭州玩一天，想吃本帮菜，下午看个展，晚上回来。"随变追问一句"几点能出门、预算大概多少"，然后给出三套计划卡：

| | 稳妥 | 紧凑 | 省钱 |
|---|---|---|---|
| 安排 | 8:05 高铁 → 西湖边午饭 → 浙江省博物馆 → 17:40 返程 | 7:20 高铁 → 早午饭 → 博物馆 → 西溪湿地 → 19:40 返程 | 8:05 高铁 → 地铁出行 → 小店午饭 → 免费展馆 → 18:50 返程 |
| 全程顺利的把握 | 91% | 68% | 84% |
| 最薄弱环节 | 午饭排队 | 湿地到车站只留 25 分钟 | 午饭离展馆远，步行 1.2 公里 |
| 人均花费 | 约 260 元 | 约 310 元 | 约 180 元 |

小林选了"稳妥"。随变一键部署：三个人的日历写入行程，设好周六 7:15 的出门提醒，列出待办"订高铁票、订午餐位、预约博物馆"，每一项点开直接跳到对应 App 的页面，由小林自己下单。

周六当天：8:05 高铁、11:30 餐厅订位、14:00 博物馆预约、17:40 返程。高铁晚点 25 分钟，下午又有雷阵雨。随变推演连锁影响：餐厅订位只有 38% 的把握赶上；博物馆在室内，不受雷雨影响；饭后原本要沿湖边步行去博物馆，现在要改成打车。它给出甲、乙、丙三个方案，并说明为什么"全都保住"做不到。用户选定后，它调起导航、起草给餐厅的消息、更新三个人的行程页面。晚上回程后生成复盘，并更新"出站到打车平均要多久"等个人参数。

后续可以低成本扩展的场景有赶飞机、看演出、接站接人、预约办事。它们复用同一个引擎，只是换一套场景模板。

### 2.3 完整闭环（对应通用要求1）

通用要求1是"理解需求—提供方案—用户行动—反馈调整"。随变把它落到一次计划的完整生命周期上：

```
① 理解需求             ② 提供方案                    ③ 用户行动              ④ 反馈调整
一句话 / 截图 / 日历 →  行前：2–3 套计划比较      →  一键部署          →   复盘 + 画像更新
   → 计划图             途中：变化推演 + 方案卡       途中：确认后执行
（行前）                （行前 + 途中）               （行前 + 途中）         （行后）
     ↑                                                                            │
     └──────── 画像让下一次生成的计划更合节奏、推演更准、方案更合口味 ←──────────┘
```

| 阶段 | 用户看到什么 | 系统在做什么 |
|---|---|---|
| ① 理解需求 | 说一句话就有候选计划；已有的安排可以用截图或日历导入；都能在计划图里逐项修改 | 大模型把输入解析成意图、约束和人；已有计划直接转成计划图，新计划交给生成器 |
| ② 提供方案 | 行前：2–3 套计划并排比较，每套标把握、最薄弱环节和花费。途中：变化发生时看到方案卡 | 生成器用高德 POI 和路径规划排程，蒙特卡洛推演给出概率并筛掉不稳的；途中由方案搜索生成候选；大模型只负责解释 |
| ③ 用户行动 | 行前：一键部署，日历、出门提醒和"待订清单"一次到位。途中：一键确认，调起导航、改日历、起草消息 | 按动作分级执行；下单、付款、发消息都由用户在对应 App 里最后点击 |
| ④ 反馈调整 | 复盘卡显示"计划 vs 实际"，画像页显示学到了什么 | 贝叶斯更新个人时间参数，从用户的选择中学习取舍偏好；两者都会用到下一次的生成和应变 |

## 三 功能清单与分级

分级规则如下。P0 是初赛（2027-01-15）必须跑通的最小完整闭环。P1 在区域赛（2027-04-15）前完成。P2 是国赛加分项，做不完也不影响主线。

### 模块1 计划生成与汇聚（理解需求）

| 编号 | 功能 | 实现方式 | 级别 |
|---|---|---|---|
| 1.1 | 一句话录入已有安排，例如"周六和小王小李去杭州，8:05 的高铁" | 大模型函数调用，输出计划图 JSON；地点用高德地理编码补全 | P0 |
| 1.2 | 截图导入：订单截图、聊天截图、预约短信截图 | 系统分享菜单把图片传给 App，端上 OCR 识别文字，再由大模型抽取字段 | P0 |
| 1.3 | 读取日历里的课程和约会 | Android CalendarContract，只读，用户授权 | P0 |
| 1.4 | 计划图可视化和逐项编辑 | Compose 时间轴视图，每个字段都可以改 | P0 |
| 1.5 | 通知识别：订单通知、变更通知（晚点、改约、取消） | NotificationListenerService，用户授权，可按应用开关；不用无障碍服务 | P1 |
| 1.6 | 聚会发起：成员通过 H5 填可用时间和偏好，系统找共同时段、挑"公平地点" | H5 + 服务端；公平地点的标准是最小化"最远那个人的路程"，候选来自高德 POI 搜索 | P1 |
| 1.7 | **一句话生成候选计划**：只说目的和偏好（"周六去杭州玩一天，想吃本帮菜"），得到 2–3 套风格不同的计划（稳妥/紧凑/省钱），每套标把握、最薄弱环节、花费 | 大模型只抽意图和约束、列活动类型；地点来自高德 POI 搜索，路程来自高德路径规划，排程和打分由自研生成器完成，见 4.9 | P0 |
| 1.8 | **一键部署**：选定一套后，写入日历、设好出门提醒、生成"待订清单"（车票、订位、预约），每项点开跳到对应 App 页面由用户自己下单 | CalendarContract 写入（预览后确认）；WorkManager 定时提醒；待订清单走深链或网页跳转，复用 5.3 和 5.6 的实现 | P0 |

### 模块2 计划体检（行前提供方案）

| 编号 | 功能 | 实现方式 | 级别 |
|---|---|---|---|
| 2.1 | 顺利概率和最薄弱环节，例如"72% 一切顺利，最弱的是 11:30 餐厅，缓冲只有 10 分钟" | 蒙特卡洛推演，见 4.3 | P0 |
| 2.2 | 出发时刻建议：什么时候出门才能按设定把握赶上 | 在推演结果上反求出门时间，计入个人准备时间 | P0 |
| 2.3 | 出行准备提醒：带伞、证件、充电宝 | 规则加天气，规则按活动类型配置 | P1 |
| 2.4 | 预案：提前算好常见变化（下雨、晚点 30 分钟）的应对，离线可看 | 行前对最薄弱的两三个环节批量跑方案搜索，结果缓存在本地；生成的计划卡上直接显示"如果下雨就……" | P1 |

### 模块3 变化感知（理解场景变化）

| 编号 | 变化来源 | 实现方式 | 级别 |
|---|---|---|---|
| 3.1 | 天气：降水、雷雨、高温 | 和风天气分钟级降水和逐小时预报；只在计划时段前后轮询 | P0 |
| 3.2 | 路况：预计路程变长 | 高德路径规划，返回带实时路况的预计时间；出发前定时刷新 | P0 |
| 3.3 | 一句话报告："我晚到 20 分钟""餐厅说没位了" | 本人或同行人在 App/H5 输入，大模型解析成变化事件 | P0 |
| 3.4 | 通知和短信里的变更 | 复用 1.5，规则加大模型分类 | P1 |
| 3.5 | 进度落后：定位显示还没出发或走得慢 | 前台定位，只在计划进行中开启，可关闭 | P1 |
| 3.6 | 航班、列车动态查询 | 接口能申请到就接入；申请不到就用 3.3 和 3.4 兜底 | P2 |

### 模块4 应变方案（途中提供方案）

| 编号 | 功能 | 实现方式 | 级别 |
|---|---|---|---|
| 4.1 | 连锁影响：哪几步受影响，每一步还有多大把握 | 把变化写进计划图后重新推演 | P0 |
| 4.2 | 方案卡：两三个方案，每个标明时间、花费、把握、需要做的动作和代价 | 方案搜索（4.4）加大模型生成说明 | P0 |
| 4.3 | 依据面板：每个数字从哪来、什么时候取的、是实测还是估计 | 每个数值都带来源标签，界面上可以展开查看 | P0 |
| 4.4 | 冲突解释："为什么不能全都保住"，以及"至少要放弃哪一项" | 求最小放宽集，见 4.5 | P1 |
| 4.5 | 追问和改方案："不想打车""能不能不去博物馆" | 大模型把用户的话转成新约束，再搜索一次 | P1 |

### 模块5 确认执行（用户行动）

| 编号 | 动作 | 实现方式 | 级别 |
|---|---|---|---|
| 5.1 | 调起导航、公交或骑行路线 | 高德 URI 调起高德地图 App | P0 |
| 5.2 | 起草消息，用户自己点发送 | 短信用 ACTION_SENDTO 预填正文；微信、QQ 走系统分享 | P0 |
| 5.3 | 修改日历 | App 内预览改动，用户确认后写入 | P0 |
| 5.4 | 常驻通知倒计时："还有 12 分钟出门" | 前台服务加常驻通知；P1 适配 Android 16 实时更新通知和 ColorOS 流体云 | P0/P1 |
| 5.5 | 同行人同步：H5 上实时显示新计划，可以回"收到"或"有异议" | FastAPI + WebSocket，链接有过期时间 | P1 |
| 5.6 | 跳转订单页做改签或退订，不代付不代退 | 深链或网页跳转到对应 App 或官网 | P1 |
| 5.7 | 耳机播报加语音确认、手表一键确认 | 耳机：TTS 加语音识别，或耳机按键；手表：Wear OS 伴随应用，退路是通知镜像 | P1 |
| 5.8 | 碰一碰把计划分享给同行人 | 接入 OPPO 超级碰一碰（附件2 能力清单） | P2 |

### 模块6 复盘与画像（反馈调整）

推演引擎只写一份 Python 代码，放在服务端。这样线上服务和离线评测用的是同一套逻辑，评委问"评测结果能不能代表线上效果"时有底气。手机离线时显示最近一次推演结果，并标注"x 分钟前"。

### 4.2 计划图：把计划变成机器能算的结构

一个计划就是一张有向图。

**节点是活动**，每个活动有这些字段：

| 字段 | 含义 | 例子 |
|---|---|---|
| 类型 | 出行、停留、订单、会面 | 停留：午餐 |
| 地点 | 高德 POI 或坐标 | 某餐厅 |
| 时间窗 | 最早开始、最晚开始 | 11:15–11:45 |
| 时长 | 一个分布，不是一个数 | 均值 60 分钟 |
| 硬 / 软 | 硬：错过就作废（发车、预约入场截止）；软：可以协商或放弃 | 软 |
| 关联订单 | 能不能改、改的费用、截止时间 | 订位可免费改到 12:30 |
| 参与人 | 谁必须在场 | 三人 |
| 来源 | 这条信息从哪来 | 截图识别，用户已确认 |

**边是先后关系和路段**。路段带交通方式和时长分布，例如"高铁站 → 餐厅，打车，高德 ETA 22 分钟"。

三个场景用同一套结构，只是模板不同：S1 是"出门 → 路段 → 上课（硬）"三个节点；S2 多了"每个成员各自一条路段"；S3 是十个左右节点的链。节点数一般不超过 20，所以后面的计算都很轻。

### 4.3 变化推演：算出"还有多大把握"

**第一步，给每个路段一个时长分布。**

```
路段时长 = 高德实时 ETA × 个人系数 × 情境修正
```

- 高德 ETA 已经包含实时路况。
- 个人系数来自画像（4.6），例如"你步行比高德估计慢 12%"。新用户先用默认值，界面标"默认估计"。
- 情境修正是一张规则表，例如下雨时步行乘 1.15、骑行不可用，早晚高峰打车加等车时间。初值是团队设定的经验值，界面如实标注；之后用自己采集的数据校准。

**第二步，蒙特卡洛采样。** 每个路段和活动时长各抽 2000 次样本，按计划图的先后顺序往下推：

```
某活动的开始时间 = max(到达时间, 时间窗最早开始)
硬约束满足 ⇔ 开始时间 ≤ 时间窗最晚开始
```

用 NumPy 向量化，20 个节点、2000 个样本，一次推演在 50 毫秒以内。

**第三步，输出三样东西。**

1. **顺利概率**：所有硬约束同时满足的样本比例。
2. **最薄弱环节**：单独满足概率最低的那个活动，以及它的缓冲时间。
3. **出发时刻**：在出门时间上二分查找，找到"最晚还能保证把握 ≥ 设定值"的时刻。

**把握的设定值**由用户选，默认 90%。这就是概率时间网络（pSTN）里的机会约束思路：不要求"一定赶上"，而是要求"赶上的概率不低于用户能接受的值"。这比"提前 30 分钟出门"这类固定规则更讲道理，也是技术深度的主要来源。

### 4.4 方案搜索：生成并比较候选方案

**算子**是对计划图的一次修改，一共六种：

| 算子 | 例子 |
|---|---|
| 换交通方式 | 骑车改公交，步行改打车 |
| 调整时间 | 午餐推迟到 12:30，出门提前 10 分钟 |
| 放弃软活动 | 取消饭后的湖边步行 |
| 换同类地点 | 换一家离车站近的餐厅（高德周边搜索） |
| 改订单 | 改订位时间、改签；计入改退费用，执行时只跳转 |
| 分组 | 先到的人先开始，后到的人直接去下一站 |

**搜索过程：**

1. 把一到两个算子组合起来，生成几十到几百个候选。
2. 大模型可以另外提出最多三个候选，但必须用算子表达，才能进入推演验证。大模型想出的方案和规则生成的方案用同一把尺子量。
3. 每个候选都跑一次 4.3 的推演，不满足机会约束的直接淘汰。
4. 剩下的按代价排序：

```
代价 = w时间 × 时间损失 + w花费 × 额外花费 + w体力 × 步行和换乘
     + w社交 × 让别人等的"人·分钟"和改约次数 + 放弃的软活动价值
```

5. 取帕累托前沿上的方案，再挑主算子不同的两三个展示。这样方案卡上的方案之间有真正的差别，而不是三个差不多的版本。

权重 w 来自画像里的取舍偏好（6.4），P0 阶段用默认权重。

### 4.5 冲突解释：说清"为什么不能全都保住"

如果没有任何候选能同时保住全部软活动，就找**最小放宽集**：最少放弃哪几个软约束，计划才能满足机会约束。

一个计划的软约束一般不超过 8 个，按集合大小从小到大枚举，最多 256 种组合，每种跑一次推演，计算量可以接受。输出例子：

> "餐厅订位和饭后湖边步行最多只能保住一个。两个都保住时，赶上 17:40 返程的把握只有 35%。"

这一项借鉴了冲突导向放宽的思路。它让用户明白取舍的原因，对应评审第四项"信息来源与操作清晰可信"。

### 4.6 画像：越用越准，而且看得见、改得了

**个人时间参数（P0）。** 每次计划结束，执行日志里有"高德预计 18 分钟，实际 21 分钟"这样的记录。我们对 `log(实际 / 预计)` 做正态共轭的贝叶斯更新：

- 记录少时结果接近默认值，记录多了才逐渐偏向个人数据，不会被一两次意外带偏。
- 按情境分层：步行、骑行、公交、打车，高峰和非高峰分开估。
- 画像页每一项都显示"基于 n 次记录"和可信区间，用户可以改数值、删记录、暂停学习。

能学的参数举例：出门准备时间、各交通方式的速度系数、"说 5 分钟到实际要多久"、在车站和景点的换乘时间。

**取舍偏好（P1）。** 每次用户在方案卡上选了一个方案，就是一条"在这几个里更喜欢这个"的记录。用条件 Logit 模型在线更新 4.4 里的权重 w，并加正则让它不偏离默认值太远。画像页把权重画成几根偏好条（省时 / 省钱 / 少走路 / 少麻烦别人），用户可以手动拖动修正。

**实际时间从哪来：** 用户在 App 或手表上点"到了"；开启定位时自动记录到达；复盘卡上用户可以补填或更正。

### 4.7 大模型的边界

| 大模型做 | 大模型不做 |
|---|---|
| 把一句话、截图文字、通知解析成计划图 JSON（按 JSON Schema 约束输出，用户确认后生效） | 不产生任何数字。时间、概率、价格、距离全部来自工具和推演，说明文字里的数字由模板填入 |
| 从"周六去杭州玩一天，想吃本帮菜"这类话里抽出意图、约束、活动类型和偏好，交给计划生成器（4.9） | 不推荐具体地点，不编营业时间和票价。地点只能从高德 POI 搜索结果里选 |
| 把用户追问（"不想打车"）转成约束或算子 | 不直接调用执行动作。所有动作都要经过动作分级关卡（第五节） |
| 额外提出候选方案（必须用算子表达，再交给推演验证） | 不读聊天全文。截图只在端上 OCR，上传的是抽取后的字段 |
| 生成方案说明、消息草稿、复盘总结 | 不替用户决定。方案卡永远给两到三个选项 |

模型选用国内已备案、支持函数调用的大模型 API，具体型号在初赛前按解析准确率和延迟实测后定。P1 尝试端侧小模型做通知分类，做不成就继续用规则加云端模型。

### 4.9 计划生成：一句话变成 2–3 套可选计划

**结论：** 生成计划和应变用的是同一套引擎。应变是"在已有计划图上用算子改"，生成是"从空白开始排出计划图"，然后都交给 4.3 推演、4.4 打分。新写的代码只有排程器，大约是方案搜索的一半工作量。

**输入。** 用户说一句话，例如"周六和小王小李去杭州玩一天，想吃本帮菜，下午看个展，晚上回来"。大模型按 JSON Schema 输出：城市、日期、出发地、同行人、预算倾向、必须项（返程、展览）、偏好（本帮菜），缺了关键项（比如几点要到家）就追问一次。

**第一步：活动骨架。** 大模型只列活动类型和大致顺序，例如"去程 → 上午景点 → 午餐（本帮菜）→ 下午展览 → 自由活动 → 返程"。这一步不出现任何具体地点和时间。

**第二步：地点候选。** 每个活动槽用高德关键词搜索或周边搜索取前 5 个 POI。营业时间、预约要求能从 POI 数据拿到就用，拿不到就用同类场所的默认值，界面标"默认估计，请确认"。

**第三步：排程。** 枚举每个槽选哪个地点、软活动的先后顺序。3–6 站、每槽 5 个候选，组合数在几百到几千之间。先用直线距离和时间窗剪掉明显不可行的，剩下几十个再调高德路径规划拿真实路程（同一对地点只查一次，结果缓存）。

**第四步：推演和打分。** 每个候选跑 4.3 的蒙特卡洛推演，不满足机会约束的淘汰；剩下的按 4.4 的代价函数打分。

**第五步：多样化挑选。** 在帕累托前沿上挑三套：**稳妥**（把握最高）、**紧凑**（活动最多）、**省钱**（花费最低）。如果两套几乎一样就只展示两套。每套计划卡上写把握、最薄弱环节、预计花费和返程时间。

**生成之后。** 用户选中的计划就是一张普通的计划图：一键部署（1.8）写日历、设提醒、列待订清单；途中照常感知、推演、出方案卡；结束后照常复盘、更新画像。用户画像也反过来影响生成，例如步行系数高的人，生成器会少排步行段。

**和"AI 攻略"的区别：**

| | 常见 AI 行程规划 | 随变 |
|---|---|---|
| 地点和时间从哪来 | 以推荐为主，停留时长和衔接时间多是估的 | 地点来自 POI 搜索，路程来自路径规划，大模型不出数字 |
| 给几套 | 通常一套 | 2–3 套风格不同、可并排比较 |
| 能不能走通 | 不评估 | 每套标把握和最薄弱环节 |
| 出发以后 | 不管 | 同一张计划图继续应变、复盘、更新画像 |

**P0 范围和退路。** P0 只做一座城市、一天以内、最多 6 站；多人一起生成（结合 1.6 的公平选址）放到 P1。如果某个活动槽搜不到合适地点，或所有候选都不满足机会约束，就告诉用户卡在哪一步，请用户直接说出想去的地方，退回"一句话录入"（1.1）的路径。

## 五 可信可控（对应评审第四项、通用要求2和5）

### 5.1 自主等级：用户决定随变能做到哪一步

| 等级 | 随变做什么 | 默认 |
|---|---|---|
| L0 只提醒 | 告诉你有变化、影响多大 | |
| L1 给方案 | 再给出方案卡，你自己去操作 | |
| L2 确认后执行 | 你点一下，它调起导航、写日历、起草消息 | ✔ 默认 |
| L3 低风险自动（P1） | 只影响你自己、可撤销的动作自动做，例如更新 App 内计划、调整提醒时间；做完通知你 | |

等级可以按计划单独设，例如"聚会用 L1，赶课用 L3"。

### 5.2 动作分级表：写在代码里，不靠大模型自觉

| 类别 | 动作 | 处理方式 |
|---|---|---|
| 自动 | 查询天气和路况、重新推演、更新 App 内计划 | 直接做，记日志 |
| 一键确认 | 写日历、调起导航、打开打车 App | 弹确认，点"好"才执行 |
| 预览后确认 | 给别人发的消息、共享位置、同步给同行人的新计划 | 先展示全文和接收人，用户可编辑，最后由用户在短信或微信里自己点发送 |
| 只跳转 | 支付、退订、改签、预约 | 只打开对应页面，随变不填表、不提交 |
| 代码里不存在 | 自动支付、自动发送消息、上传聊天全文 | 没有这些接口，评委可以看源码验证 |

执行器只接受动作类型在白名单里的请求，大模型输出里如果出现不在白名单的动作，直接丢弃并记录。这一点在 AI 代码评测里也能体现。

### 5.3 来源标签：每个数字都说清楚从哪来（通用要求2）

| 标签 | 例子 |
|---|---|
| 实时接口 | "高德实时路况 · 07:05 获取" |
| 天气预报 | "和风天气分钟级降水 · 07:04 获取" |
| 用户提供 | "小王 18:10 报告" |
| 画像估计 | "你的步行系数 1.12 · 基于 23 次记录" |
| 默认估计 | "默认值，还没有你的数据" |
| 演示数据 | 回放模式下所有数据都带"演示"水印 |

方案卡上的每个概率和时间都可以点开，看到它用到了哪些标签的数据。

### 5.4 授权与隐私

- **授权中心**：日历、通知、定位、短信草稿各一行，写明用途、最近一次使用时间，一键撤销。
- **按需授权**：第一次用到某个能力时才申请，不在启动时一次要全部权限。
- **最小上传**：通知和截图在端上处理，服务端只收结构化的计划字段。同行人 H5 只看得到这次计划里和他有关的部分，链接到期失效。
- **不用无障碍服务**：避免读屏带来的隐私风险，也避免上架审核问题。

## 六 跨应用、跨设备、跨场景（对应评审第二项）

| 维度 | 随变怎么做 | 用户少做了什么 |
|---|---|---|
| 跨应用 | 读：日历、通知、截图（来自任何 App）。写：高德导航、日历、短信、微信分享、订单页跳转 | 不用在地图、天气、聊天、订单 App 之间来回切 |
| 跨设备 | 手机做主控；手表显示倒计时和一键确认；耳机播报变化并语音确认；同行人用浏览器打开 H5 | 走路、骑车、拎行李时不用掏手机 |
| 跨人 | 聚会时间收集、变化同步、"收到 / 有异议"回执 | 不用在群里一个个问、一个个通知 |
| 跨场景 | 同一个引擎跑赶课、聚会、短途；画像在场景之间共享，例如步行系数在赶课里学到，短途里也能用 | 每个场景不用重新教一遍 |

**系统级的意思**：随变不是又一个需要用户主动打开的 App，而是驻留在通知、手表和日历里，在变化发生的那一刻出现。对 OPPO 手机，P1 适配流体云，P2 接入超级碰一碰分享计划。

## 七 可行性审查：每项都说清靠什么做、做不成怎么办

难度：★ 调接口即可；★★ 要写一些逻辑或适配；★★★ 有不确定性，必须先验证。

| 能力 | 用到的接口或技术 | 难度 | 做不成的退路 |
|---|---|---|---|
| 一句话 / 截图建计划 | 大模型函数调用 + JSON Schema；ML Kit 端侧 OCR | ★★ | 解析错的字段让用户在编辑页改；准确率写进评测 |
| 一句话生成计划 | 大模型抽意图和活动骨架；高德关键词 / 周边搜索取 POI；高德路径规划；自研排程器复用推演和方案搜索 | ★★ | 营业时间缺失时标"默认估计"让用户确认；生成失败时说明卡在哪一步，请用户说出具体地点，退回一句话录入 |
| 一键部署 | CalendarContract 写入；WorkManager 提醒；待订清单用深链或网页跳转 | ★ | 某个 App 没有深链就打开网页版 |
| 读日历 | CalendarContract | ★ | 无 |
| 路线和实时 ETA | 高德 Web 服务路径规划（个人开发者免费额度够开发和小规模试用） | ★ | 超额时降低刷新频率 |
| 天气 | 和风天气分钟级降水、逐小时预报 | ★ | 只用逐小时预报 |
| 导航执行 | 高德地图 URI 调起 | ★ | 打开网页版路线 |
| 短信草稿 | ACTION_SENDTO 预填正文 | ★ | 无 |
| 微信 / QQ 草稿 | 系统分享菜单发文字 | ★★ | 复制到剪贴板并打开微信，提示用户粘贴 |
| 精确时刻提醒和后台感知 | 计划时段内开前台服务；精确闹钟 | ★★ | 引导用户把随变加入自启动和电池白名单；做不到时退回到"打开 App 时刷新" |
| 蒙特卡洛推演、方案搜索、冲突解释 | Python + NumPy，自研 | ★★ | 规模小（≤20 节点），性能不是问题；难点是正确性，靠回放集测试 |
| 贝叶斯画像 | 自研，几十行代码 | ★ | 无 |
| 偏好学习 | 条件 Logit 在线更新 | ★★ | 数据不够时只用默认权重加手动拖动 |
| 聚会 H5 和同步 | FastAPI + WebSocket + 静态 H5 | ★★ | WebSocket 不稳时改成轮询 |
| 通知识别 | NotificationListenerService | ★★ | 不同 App 通知格式不同，先覆盖 5 到 8 个常用 App；其余靠截图和一句话 |
| 流体云 / 实时更新通知 | Android 16 实时更新通知；ColorOS 流体云开放能力 | ★★★ | 普通常驻通知加倒计时，功能不受影响 |
| 手表 | 保底：手机通知镜像到手表（多数手表都支持）；加分：Wear OS 伴随应用 | ★★★ | 国内不少手表不是 Wear OS，必须先在测试机上验证；做不成只保留通知镜像 |
| 耳机语音确认 | Android TTS + 语音识别；或耳机按键 | ★★ | 只播报，不做语音确认 |
| 航班 / 列车动态 | 第三方商业接口，需要申请，可能收费 | ★★★ | 用户一句话报告晚点，或从通知里识别；P2，不影响主线 |
| 实时公交到站 | 没有统一的开放接口 | — | 不做。用高德公交路线的计划时间加个人等车时间估计 |
| 超级碰一碰 | OPPO 开放能力（附件2） | ★★★ | 用二维码分享计划链接 |

**结论：** P0 的 25 项全部是 ★ 或 ★★，没有依赖拿不到的接口。★★★ 的都是 P1、P2 加分项，而且都有不影响主线的退路。

**团队 AI 编程分工建议：** 接口适配、界面、H5、CRUD 交给 Claude 或 Codex 生成，人重点写和审推演引擎、动作分级关卡、评测脚本。这三处决定技术分和 AI 代码评测，必须自己完全看懂。

## 八 验证方案（对应通用要求4、评审第五项）

验证分两部分：离线评测证明"算得对"，真实试用证明"有人用、有用"。

### 8.1 离线评测：日常变化回放集

**回放集是什么：** 每一条是"一个计划 + 一串变化事件 + 正确答案"。例如"三人短途，8:05 高铁晚点 25 分钟，14:30 起雷阵雨"，正确答案是"受影响的是餐厅和饭后湖边步行，博物馆在室内不受影响"。

另建一个**生成测试集**：初赛前 30 句、区域赛前 80 句"一句话需求"（城市、人数、偏好各不相同），用来评计划生成。

| 项目 | 初赛前 | 区域赛前 |
|---|---|---|
| 条数 | 60 条 | 150 条 |
| 来源 | 团队成员自己的真实计划、试用用户的真实记录、在真实计划上人工加扰动生成的合成样本 | 同左，真实样本占比提高到一半以上 |
| 标注 | 两人独立标注受影响环节和可行方案，不一致时讨论 | 同左 |

每一条都标"真实"或"合成"，报告里分开统计（通用要求2）。

**指标和对照组：**

| 指标 | 衡量什么 | 对照组 |
|---|---|---|
| 解析准确率（字段级 F1） | 一句话和截图建计划准不准 | 无 |
| 影响识别 F1 | 有没有找对受影响的环节 | 纯大模型：把计划和变化直接交给大模型判断 |
| 方案可行率 | 给出的方案是否真的满足所有硬约束 | 纯大模型方案；同时统计大模型方案里时间、距离数字的错误率 |
| 概率校准（Brier 分数、校准曲线） | 说 90% 的时候是不是真的大约九成能成 | 固定规则："提前 N 分钟出门" |
| 感知延迟 | 变化发生到用户收到提醒的时间 | 无 |
| 生成计划可行率 | 生成的计划是否营业时间、预约、路程全部对得上 | 纯大模型直接写行程；同时统计它的地点不存在率和时间错误率 |
| 生成计划多样性 | 2–3 套计划之间是否真有差别（不同地点数、把握差、花费差） | 同一个大模型连续生成三次 |

纯大模型对照组很重要，它直接回答评委"为什么不直接问大模型"。

### 8.2 操作成本对比

找 8 到 10 名同学，每人完成三个标准任务（例如"下雨了，重新安排去上课"、"有人迟到，通知所有人改时间"），一次手动操作，一次用随变。记录用时、App 切换次数、点击次数。这组数据用来证明"减少反复查找和切换"。

### 8.3 真实试用

| 阶段 | 人数和时长 | 收集什么 |
|---|---|---|
| 初赛前 | 10–15 人，2 周（2026-12-28 至 2027-01-10） | 每人每周计划数、方案采纳率、误报率（用户点"没用"的比例）、访谈 8 人 |
| 区域赛前 | 30 人以上，4 周 | 上面全部，加周留存、SUS 可用性量表、概率校准的真实数据、画像学习前后的预测误差 |

招募对象是本校同学，覆盖走读和住校、常骑车和常坐公交的人。数据全部匿名，试用前签知情同意。

## 十三 评委追问预案

**问：高德、日历本来就有出发提醒，你多做了什么？**
答：它们只看一段路，不知道后面还有餐厅订位、博物馆预约和同行的人。随变看的是整个计划的连锁影响，给出可比较的方案，并协助改日历、通知别人。

**问：高德、小红书和各家大模型都能一句话出行程了，你们的生成有什么不同？**
答：它们一般给一套推荐行程，出发后就不管了。随变给 2–3 套风格不同的计划，每套标出把握和最薄弱环节，地点来自 POI 搜索、路程来自路径规划，不让大模型编数字；选定后同一张计划图继续盯变化、出方案、做复盘。8.1 里有和纯大模型行程的可行率对比。

**问：一句话生成计划，会不会变成另一个攻略 App？**
答：不会。P0 只排一天内 3–6 站的时间、地点、路线和订单，不写景点介绍和种草内容。生成只是闭环的起点，比赛重点在后面的应变和复盘。

**问：TripIt 这类行程管理 App 呢？**
答：它们主要面向航班和商旅，以提醒为主。随变面向日常的多环节、多人计划，重点在变化后的方案和确认执行。

**问：为什么不直接把计划丢给大模型？**
答：看 8.1 的对照数据。大模型会编时间和距离，方案也不一定满足硬约束。随变让大模型负责理解和表达，数字全部来自接口和推演。

**问：93% 这个数字可信吗？**
答：看校准曲线。说 90% 的那些计划实际成功率是多少，我们如实报告。数据少的项目会标"默认估计"。

**问：让用户录计划太麻烦，谁会用？**
答：没有计划时说一句话就能生成；已有安排时日历自动读，截图分享一下就能导入，通知能自动识别（P1）。用户只需要确认，不需要手填。试用数据里的每周计划数可以回答这个问题。

**问：同行的人不装 App 怎么办？**
答：H5 链接，浏览器打开就能填时间、看新计划、回"收到"。

**问：隐私怎么保证？**
答：聊天和通知原文不出手机；授权可以随时撤销；画像可以查看、修改、删除、暂停；源码里没有自动支付、自动发消息的接口。

**问：代码有多少是 AI 写的？**
答：界面、接口适配、H5 大量用 AI 生成；推演引擎、动作分级关卡和评测脚本由我们自己写、自己审，并有单元测试和回放测试覆盖。
