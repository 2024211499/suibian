# 随变 技术执行方案（开发用）

配套文档：《随变_竞赛方案_v2.md》。本文的功能编号（1.1–7.5）、P0/P1/P2 划分和 4.x 算法章节都与 v2 一一对应。v2 讲"做什么、为什么能拿分"，本文讲"怎么写出来"。

---

## 〇 先回答三个问题

### 0.1 功能还要不要加？

**不加。** P0 的 25 项已经覆盖赛题2的六个评审点和五条通用要求，再加功能只会摊薄完成度。复赛起应用和技术各占 30 分，比的是试用数据和评测，不是功能数。

**要细化的是流程。** v2 写清了"有什么"，没写清"什么时候、按什么顺序、失败了怎么办"。本文补齐了以下八处，开发时以本文为准：

| 细化项 | 本文位置 | 不细化会出什么问题 |
|---|---|---|
| 计划生命周期状态机 | 第八节 | 各端对"计划现在处于哪一步"理解不一致，提醒乱发 |
| 感知调度（什么时候查天气路况、多久查一次） | 8.3 | 要么耗电被系统杀，要么变化来了没发现 |
| 后台保活在国产手机上的具体做法 | 10.3 | OPPO 手机没有谷歌服务，照抄网上的 FCM、Geofencing 教程跑不起来 |
| 动作确认关卡的代码结构 | 第十二节 | 评委问"怎么保证不会自动发消息"时拿不出代码 |
| 冷启动默认值 | 7.6 | 新用户第一次用时概率没有依据 |
| 复盘的提问顺序 | 8.5 | 用户懒得填，画像学不到东西 |
| 每次生成的高德调用预算 | 6.4 | 生成一次要等一分钟，或者一天就把额度用完 |
| 大模型失败时的降级路径 | 5.6 | 大模型超时或输出乱码时整个流程卡死 |

### 0.2 模型要不要自己本地开发？

**不需要训练或本地部署大模型，直接调用云端 API 就行，这不会扣分。** 理由有四条：

1. 赛题通用要求3只要求"分清自研和复用"，没有要求自训模型。评委看的是你在模型之外做了什么。
2. 随变的技术深度在自研的推演引擎、方案搜索、计划生成器和贝叶斯画像（v2 第四节），这些都是自己写的算法，不是大模型。大模型只做理解和表达（v2 4.7）。
3. 你们没有训练数据，也没有 GPU。本地跑 7B 级小模型，中文 JSON 抽取的稳定性明显不如云端模型，还要多维护一套推理服务。
4. 上架国内商店时，调用已备案的大模型只需做"大模型登记"。自己部署模型反而要走更重的备案流程。

整个系统用到三类"模型"，在计划书里要分开写清楚：

| 类别 | 是什么 | 自研还是复用 |
|---|---|---|
| 云端大模型 | 意图解析、活动骨架、追问转约束、文字解释和消息草稿 | 复用（API 调用） |
| 自研算法模型 | 蒙特卡洛推演、算子方案搜索、排程生成器、最小放宽集、贝叶斯画像 | 自研 |
| 端侧小模型 | 截图文字识别（ML Kit 中文 OCR，离线运行） | 复用 |

### 0.3 直接调用的话调哪个？

**主用阿里云百炼的通义千问（qwen-plus，简单任务用 qwen-flash），备用 DeepSeek（V4 系列的 Flash 模型）。** 两家都是国内已备案模型，都兼容 OpenAI 接口格式，都支持 JSON 输出和函数调用，所以代码里只写一个客户端，换模型只改配置。

| | 通义千问（百炼） | DeepSeek |
|---|---|---|
| 角色 | 主用 | 备用，主用超时或报错时自动切换 |
| 接入地址 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `https://api.deepseek.com` |
| 选它的理由 | 同一平台还有视觉模型（qwen-vl），可做截图识别的兜底；新账号有免费额度 | 便宜，中文能力强，上下文长 |
| 参考价格（2026 年下半年公开报价） | qwen-plus 约 $0.40 / $1.20 每百万输入/输出 token；qwen-flash 约 $0.05 / $0.40 | Flash 约 $0.15 / $0.60（闲时），$0.30 / $1.20（忙时）；无免费额度 |

价格和模型名会变，**开发第一天在两家控制台确认当前的模型 ID 和价格**，写进 `.env`，代码里不要写死。DeepSeek 在 2026 年 4 月发布 V4 时已停用旧的 `deepseek-chat` 名称，网上旧教程里的模型名可能已经失效。

**按比赛规模估算花费：** 一次一句话生成大约调用 3 次大模型，共约 4 千输入 token、1.5 千输出 token，用 qwen-plus 不到 1 分钱人民币。试用期 30 人、每人每天 3 次，一个月几十元以内。

**直接调用要守住的五条规矩：**

1. **密钥只放服务端。** APK 里不出现任何大模型、高德 Web 服务、和风的密钥。手机只和自己的服务端通信。
2. **最少发送、先脱敏。** 只发用户那一句话或 OCR 后的订单字段。人名换成"成员A/B"，手机号用正则打码。不发聊天全文和通知原文。
3. **大模型不产出数字。** 所有时间、概率、距离、价格由引擎算出后用模板填入，见 5.4。
4. **输出必须过 Schema 校验。** 不合格就带错误信息重试一次，再不行走规则兜底，见 5.6。
5. **大模型不能触发动作。** 它的输出里没有"动作"这个字段，只能提议算子，算子由引擎评估、由用户确认（第十二节）。

### 1.1 四个关键架构决定

| 决定 | 理由 |
|---|---|
| **引擎只放服务端（Python）** | 推演、搜索、生成要调高德，本来就要联网；NumPy 写蒙特卡洛最省事；回放评测直接复用同一份代码，评委问"评测的是不是线上代码"时答得上来。断网时手机显示上次推演结果并标"x 分钟前"。 |
| **服务端 P0 不存用户数据** | 每次请求由手机带上计划图和画像参数，服务端算完就丢（只留匿名统计）。画像和观测记录只在手机的 Room 里。隐私问题最好答，服务端也简单，P0 甚至不需要数据库。P1 做多人 H5 时才引入 PostgreSQL 存共享计划。 |
| **画像更新在手机端（Kotlin）** | 贝叶斯更新只有几十行，放在端上，画像页的查看、修改、删除、暂停都是本地操作。服务端评测脚本里有一份 Python 镜像，两边用同一组测试向量（JSON）保证结果一致。 |
| **动作分级表只写一份** | `schema/actions.yaml` 是唯一来源，构建时生成 Kotlin 枚举。执行器、授权中心、计划书里的表格都从这份文件来，不会前后不一致。 |

## 二 数据模型

所有结构先写成 `schema/*.json`，服务端用 Pydantic 模型、Android 用 kotlinx.serialization 数据类，两边都从 Schema 对照着写（或用 datamodel-codegen 生成 Python 端）。**第 1 周第一件事就是把本节定稿**，之后改字段必须两端同时改。

### 2.1 计划图 PlanGraph（v2 4.2 的落地）

时间统一用带时区的 ISO 8601 字符串（`2026-12-05T08:00:00+08:00`），引擎内部换算成"距计划日 0 点的分钟数"计算。坐标统一 GCJ-02（高德坐标系），字段名 `lng`、`lat`。

```json
{
  "plan_id": "p_7f3a", "version": 3, "scenario": "S3",
  "title": "杭州一日", "date": "2026-12-05", "city_adcode": "330100",
  "status": "DEPLOYED", "autonomy": "L2", "p_target": 0.9,
  "members": [{"id": "m0", "alias": "我"}, {"id": "m1", "alias": "成员A"}],
  "nodes": [
    {"id": "n0", "kind": "origin", "name": "家", "loc": {"lng": 120.21, "lat": 30.25},
     "src": {"tag": "user"}},
    {"id": "n2", "kind": "stay", "category": "meal", "name": "某本帮菜馆",
     "poi_id": "B0FFG8XXXX", "loc": {"lng": 120.16, "lat": 30.26},
     "window": {"earliest": "11:15", "latest": "11:45"},
     "duration": {"mean_min": 60, "sd_min": 10},
     "hard": false, "value": 3, "members": ["m0", "m1"],
     "order": {"type": "booking", "changeable_until": "12:30", "change_fee": 0,
               "deeplink": null},
     "src": {"tag": "amap_poi", "fetched_at": "2026-12-04T21:03:00+08:00"}}
  ],
  "edges": [
    {"id": "e1", "from": "n1", "to": "n2", "mode": "taxi",
     "eta_min": 22, "dist_m": 8400, "cost_yuan": 31,
     "src": {"tag": "amap_route", "fetched_at": "2026-12-05T10:41:00+08:00"}}
  ],
  "constraints": [
    {"id": "c1", "type": "arrive_by", "node": "n5", "time": "17:40", "hard": true},
    {"id": "c2", "type": "budget_max", "yuan": 300, "hard": false, "value": 2}
  ],
  "sim": null, "updated_at": "2026-12-05T10:41:05+08:00"
}
```

字段取值约定：

| 字段 | 取值 |
|---|---|
| `kind` | `origin` 出发点、`stay` 停留（上课、吃饭、景点、展览）、`meet` 会面、`hub` 车站机场、`end` 终点 |
| `category` | `class`、`meal`、`sight`、`exhibit`、`shop`、`rest`、`train`、`flight`、`other`，决定默认时长和情境规则 |
| `mode` | `walk`、`bike`、`ebike`、`bus`（公交地铁）、`taxi`、`drive`；对应高德 v5 的 walking、bicycling、electrobike、transit/integrated、driving |
| `window` | 只写时分时默认当天；`earliest` 缺省表示不限，`latest` 缺省表示软节点无截止 |
| `value` | 软节点和软约束的"放弃代价"，1–5，默认 2，用户可调；代价函数和最小放宽集都用它 |
| `src.tag` | `user`、`calendar`、`screenshot`、`amap_poi`、`amap_route`、`qweather`、`llm_parsed`（用户确认前）、`profile`、`default`、`demo`，对应 v2 5.3 的标签 |

硬性上限：节点 ≤ 20、软约束 ≤ 8、成员 ≤ 6（v2 4.2、4.5）。服务端入口直接校验，超了返回 422，不要让引擎去处理超大输入。

### 2.3 算子和方案 Option

算子用统一的结构表示，大模型提议、规则生成、用户追问三条路径最后都变成这个结构（v2 4.4）：

```json
{"op": "change_mode", "edge": "e1", "to": "bus"}
{"op": "shift_time", "node": "n2", "delta_min": 30}
{"op": "drop_soft", "node": "n4"}
{"op": "swap_place", "node": "n2", "poi_id": "B0FF...", "radius_m": 1500}
{"op": "change_order", "node": "n2", "new_time": "12:30", "fee_yuan": 0}
{"op": "split_group", "members": ["m1"], "skip_to": "n3"}
```

一个方案 Option 是 1–2 个算子加上评估结果：`{option_id, ops[], plan_after, sim, cost: {extra_min, extra_yuan, walk_m, transfers, wait_person_min, dropped_value}, score, actions[], explain}`。`actions[]` 是执行这个方案需要的动作（如"调起导航""起草消息给成员A"），每个都带动作类型，交给第十二节的关卡。

  "time_factors": {

## 三 服务端接口

所有接口前缀 `/v1`，请求和响应都是 JSON，手机每次请求带 `X-Device-Id`（安装时生成的随机 UUID）和 `X-App-Version`。P0 不做账号体系，按设备 ID 做限流（每设备每分钟 20 次）。

| 方法与路径 | 输入 | 输出 | v2 功能编号 |
|---|---|---|---|
| `POST /v1/parse` | `{text, now, city_adcode, loc?}` | `{intent, draft_plan, questions[]}` | 1.1 一句话录入已有安排 |
| `POST /v1/ocr/parse` | `{ocr_text, now}`（手机已做完 OCR） | `{order_fields, node_patch}` | 1.2 截图导入 |
| `POST /v1/generate` | `{text, now, city_adcode, origin, profile}` | `{job_id}` | 1.7 一句话生成 |
| `GET /v1/generate/{job_id}/events` | — | SSE 事件流，见 3.1 | 1.7 生成进度 |
| `POST /v1/simulate` | `{plan, profile, now, seed?}` | `{sim, evidence}` | 2.1 顺利概率、2.2 出发时刻、4.3 依据面板 |
| `POST /v1/refresh` | `{plan, now}` | `{plan_patch, changed[]}` | 3.1 天气、3.2 路况：重查并更新边的 ETA 和来源标签 |
| `POST /v1/report` | `{plan, text, now, member?}` | `{event, plan_patch}` | 3.3 一句话报告变化（"我晚到 20 分钟"） |
| `POST /v1/replan` | `{plan, profile, now, trigger}` | `{options[], relax?}` | 4.1 连锁影响、4.2 方案卡；`relax` 是 4.4 最小放宽集（P1） |

### 3.1 生成进度 SSE

一句话生成要十几秒，必须让用户看到在做什么，不然像卡死。事件按顺序发：

```
event: stage   data: {"stage":"intent","msg":"理解需求"}
event: intent  data: {...意图，手机可以先展示"我理解的是：…"}
event: stage   data: {"stage":"poi","msg":"找地点","done":3,"total":4}
event: stage   data: {"stage":"route","msg":"查路程","done":12,"total":30}
event: stage   data: {"stage":"simulate","msg":"推演 18 个组合"}
event: option  data: {...第 1 套方案，先出先显示}
event: option  data: {...}
event: done    data: {"n_options":3,"elapsed_ms":14200}
event: error   data: {"code":"AMAP_QUOTA","fallback":"parse_only"}
```

Android 端用 OkHttp 的 `okhttp-sse` 接收。断线时用 `GET /v1/generate/{job_id}` 取最终结果（结果在 Redis 存 1 小时）。

### 3.2 错误码

| 码 | 含义 | 手机端表现 |
|---|---|---|
| `LLM_FAIL` | 两家大模型都失败 | 转 1.1 手动录入表单，已识别的字段预填 |
| `AMAP_QUOTA` / `AMAP_FAIL` | 高德超额或报错 | 用直线距离 × 绕行系数估算，边标"默认估计" |
| `QWEATHER_FAIL` | 天气失败 | 不做天气修正，依据面板写"天气未获取" |
| `INFEASIBLE` | 硬约束无论如何都满足不了 | P0：说明"××最多只有 y% 把握"，给出把握最高的方案；P1：显示最小放宽集（v2 4.5 算法） |
| `TOO_LARGE` | 超过节点、约束、成员上限 | 提示拆成两个计划 |

原则：**任何外部服务失败都不能让流程停住**，只能降级并在界面上说明降级了什么。

## 四 生成流水线（v2 4.9 的落地）

`generator/pipeline.py` 是一个 async 函数，按下面六步走，每一步结束发一个 SSE 事件。总时限 20 秒，到点就用已有结果出方案。

| 步 | 做什么 | 外部调用 | 时限 |
|---|---|---|---|
| ① 意图 | 大模型按 `intent.schema.json` 抽城市、日期、出发地、同行人、必须项、偏好、预算倾向；缺"几点前到家"这类关键项时返回 `questions[]`，手机问完再继续 | 大模型 1 次（qwen-plus） | 4 s |
| ② 骨架 | 大模型按 `skeleton.schema.json` 列活动槽：类型、关键词、硬/软、先后约束。不出地名、不出时间 | 大模型 1 次 | 4 s |
| ③ 地点 | 每个槽调高德搜索取前 5 个 POI（有锚点用周边搜索，没有用关键词搜索），再用详情接口取营业时间 | 高德搜索 ≤ 6 次 + 详情 ≤ 3 次（每次最多 10 个 id） | 3 s |
| ④ 粗排 | 本地用直线距离估路程，束搜索找出约 30 个可行组合 | 无 | < 0.5 s |
| ⑤ 精排 | 只给进入前列的组合查真实路程，推演、打分、挑三套 | 高德距离 ≤ 3 次 + 路径 ≤ 15 次（只算没命中缓存的） | 7 s |
| ⑥ 说明 | 每套方案生成一句话特点，数字用占位符（5.4） | 大模型 1 次（qwen-flash，三套一起写） | 1.5 s |

### 4.1 活动槽和默认值

骨架里每个槽长这样：`{slot_id, category, keyword, hard, value, after: [slot_id], near: slot_id?}`。例如"午餐（本帮菜）"是 `{category: meal, keyword: "本帮菜", hard: false, value: 3}`。

| category | 默认停留（均值 ± 标准差） | 营业时间拿不到时的默认 |
|---|---|---|
| meal | 60 ± 10 分钟 | 11:00–14:00、17:00–21:00 |
| sight | 90 ± 20 | 08:30–17:00 |
| exhibit | 90 ± 20 | 09:00–17:00，周一闭馆 |
| shop | 60 ± 15 | 10:00–22:00 |
| rest | 30 ± 10 | 不限 |
| class | 按课表 | 按课表，硬节点 |

这些默认值写在 `server/app/generator/defaults.yaml`，用到时节点来源标 `default`，界面显示"默认估计，请确认"。营业时间从高德详情接口的 business 字段解析（`opentime_today` 或 `opentime_week`），解析失败也走默认值。

### 4.2 粗排：束搜索

```python
def coarse_search(slots, pois, origin, depart, end_by, beam=40):
    # 软活动的先后顺序最多 3! = 6 种排列，每种排列各跑一次束搜索
    results = []
    for order in feasible_orders(slots):              # 满足 after 约束的排列
        beam_states = [State(at=origin, t=depart, picked=[], cost=0)]
        for slot in order:
            nxt = []
            for s in beam_states:
                for poi in pois[slot.id] + ([SKIP] if not slot.hard else []):
                    s2 = s.extend(slot, poi, est_leg=haversine_eta)  # 直线距离 × 1.4 绕行系数 ÷ 方式速度
                    if s2.violates_window() or s2.t > end_by - est_back(s2):
                        continue                       # 时间窗或返程来不及，剪掉
                    nxt.append(s2)
            beam_states = top_k(nxt, beam, key=approx_cost)
        results += close_with_return(beam_states)
    return dedup(results)[:30]
```

交通方式在粗排阶段按距离先定：1.2 km 以内步行；1.2–4 km 骑行或公交；4 km 以上公交和打车各生成一个变体。用户说了"不想走路""不打车"时直接改这条规则。

### 4.3 精排、打分和挑三套

1. 30 个组合先用一次 `/v3/distance` 批量查真实距离和时间（一次最多 100 个起点），重新排序，留前 8 个。
2. 前 8 个组合涉及的路段去重（通常 15–25 段），先查缓存（键见 2.6）。没命中的按"出现在几个组合里"排序，最多 15 段调 v5 路径规划；剩下的用第 1 步 `/v3/distance` 的结果，节点来源标 `default`。
3. 每个组合转成 PlanGraph，套用画像系数（7.5），跑 2000 次推演。8 个组合共用同一组随机数（7.1）。
4. 按 v2 4.4 的代价公式打分，再按下表挑选。

| 方案 | 规则 | 门槛 |
|---|---|---|
| 稳妥 | p_all 最高 | 无 |
| 紧凑 | 完成的软活动价值和最大；相同时 p_all 高者优先 | p_all ≥ 0.8 |
| 省钱 | 额外花费最低（打车费按高德 taxi_cost，门票和人均消费按 POI 的 cost 字段） | p_all ≥ 0.8 |

去重规则：两套方案的 POI 集合 Jaccard > 0.7 且 p_all 相差 < 5% 时，只留一套。紧凑或省钱不达门槛就不出，界面写"只找到一套有把握的安排"。

### 4.4 超时、失败和兜底

| 情况 | 处理 |
|---|---|
| 到 20 秒还没算完 | 用已经推演完的组合出方案，`done` 事件带 `partial: true` |
| 意图解析失败两次 | 发 `error{code: LLM_FAIL, fallback: "form"}`，手机打开 1.1 录入表单，已识别的字段预填 |
| 某个槽一个 POI 都没搜到 | 硬槽：追问用户换关键词；软槽：跳过并在方案卡写明 |
| 没有任何组合满足硬约束 | 返回把握最高的一套，标"××最多只有 y% 把握"（3.2 INFEASIBLE） |
| 超出 P0 范围（跨城、多天、> 6 站） | 意图阶段直接识别，提示"目前只支持一城一天"，引导到 1.1 手动录入 |

验收标准：15 句生成测试集（W4）里，至少 13 句 20 秒内出方案；每套方案的地点都真实存在、营业时间内到达、硬约束满足。

## 五 大模型层

### 5.1 客户端和切换

`server/app/llm/client.py` 用 OpenAI 官方 Python SDK，两家都走兼容接口，只换 `base_url`、`api_key`、`model`。

```python
PROVIDERS = [
    Provider("qwen", base_url=env.QWEN_BASE, key=env.QWEN_KEY,
             models={"main": env.QWEN_MAIN, "lite": env.QWEN_LITE}),     # qwen-plus / qwen-flash
    Provider("deepseek", base_url=env.DS_BASE, key=env.DS_KEY,
             models={"main": env.DS_MAIN, "lite": env.DS_MAIN}),          # DeepSeek V4 Flash
]

async def call(task: str, messages, schema, tier="main", timeout=4.0):
    for p in healthy(PROVIDERS):            # 连续 3 次失败的服务商熔断 60 秒
        try:
            r = await p.chat(model=p.models[tier], messages=messages,
                             response_format={"type": "json_object"},
                             temperature=0.2, timeout=timeout)
            return validate_or_repair(r, schema)       # 见 5.6
        except (Timeout, RateLimit, ServerError, SchemaError) as e:
            mark_fail(p, e)
    raise LLMFail(task)
```

模型名一律写在 `.env`，不写死在代码里。两家模型名和价格以控制台为准，换模型只改配置。

### 5.2 大模型负责的任务

| 任务 | 接口 | 档位 | 输入 | 输出 Schema |
|---|---|---|---|---|
| 一句话录入解析 | parse（1.1） | main | 用户原话 + 今天日期 + 常用地点别名 | `plan_graph` 的节点和约束部分 |
| 截图文字解析 | ocr/parse（1.2） | main | 手机端 OCR 出的文字（不传图片） | 同上 |
| 生成意图 | generate ① | main | 原话 + 画像里的偏好标签 | `intent.schema.json` |
| 活动骨架 | generate ② | main | 意图 | `skeleton.schema.json` |
| 方案一句话特点 | generate ⑥ | lite | 方案的结构化差异 | `{text_tpl}` |
| 一句话报告 | report（3.3） | lite | 变化事件 + 推演前后对比 | `{text_tpl}` |
| 方案解释和消息草稿 | explain（4.2、5.2） | lite | 选中的方案 + 收件人称呼 | `{text_tpl, sms_tpl}` |
| 追问改方案 | followup（4.5，P1） | main | 追问原话 + 当前方案 | 算子列表（≤ 3 个候选） |

推演、出发时刻、概率、代价、排序都不经过大模型。

### 5.3 提示词约定

提示词放在 `server/app/llm/prompts/*.md`，每个任务一份，固定四段：角色和边界、输出 Schema（原样贴入）、3 个少样本示例、禁止事项。禁止事项统一写："不输出任何地名以外的事实；不编造时间、价格、概率；不确定的字段填 null 并放进 questions"。

提示词改动要跑一遍 `eval/run_generate.py`，结构合法率不能低于上一版。

### 5.4 大模型不产出数字

所有展示给用户的句子由大模型写模板，数字由引擎填。大模型看到的是占位符：

```json
{"text_tpl": "雨变大了，骑车改步行后你{p_after}把握按时到，比原来{delta_min}出门",
 "slots": ["p_after", "delta_min"]}
```

`render(tpl, sim)` 把占位符换成引擎的值（"86%""提前 6 分钟"）。模板里出现阿拉伯数字或未知占位符时直接判失败，改用 `templates/fallback.yaml` 里的固定句式。这条在单元测试里断言（13.1）。

### 5.5 脱敏

发给大模型之前，`llm/redact.py` 做三件事：手机号、身份证号、订单号用正则换成 `<PHONE_1>` 之类的标记；联系人姓名换成"同学A""同学B"；家和宿舍的精确地址换成"家""宿舍"。返回后再换回来。日志只存脱敏后的文本，保留 7 天。

### 5.6 校验、重试、降级

```python
def validate_or_repair(raw, schema):
    obj = json.loads(extract_json(raw))           # 去掉 ```json 包裹
    errs = list(Draft202012Validator(schema).iter_errors(obj))
    if not errs:
        return obj
    raise SchemaError(errs)                        # 外层会带着错误信息重试 1 次
```

每个任务最多调用 2 次：第 1 次失败，把校验错误拼进消息再问一次；还失败就切到另一家；两家都失败抛 `LLMFail`，按 3.2 走兜底（录入类回到 1.1 表单，文案类用固定句式）。线上统计每个任务的一次成功率，低于 95% 就改提示词。

## 六 外部服务网关

`server/app/gateway/` 下每个服务一个适配器，对外只暴露统一的函数，内部负责鉴权、限流、缓存、错误转换。上层代码不直接拼外部 URL。

### 6.1 高德

申请 Web 服务 Key（服务端用）和 Android SDK Key（手机端定位用）两个 Key，Web 服务 Key 只放服务器。

| 函数 | 高德接口 | 关键参数 | 用途 |
|---|---|---|---|
| `geocode(addr, city)` | `/v3/geocode/geo` | address, city | 地址转坐标 |
| `regeo(lnglat)` | `/v3/geocode/regeo` | location | 坐标转地址 |
| `search_text(kw, city, types)` | `/v5/place/text` | keywords, region, city_limit=true, show_fields=business | 关键词找 POI |
| `search_around(kw, center, r)` | `/v5/place/around` | location, radius, sortrule=distance | 锚点周边找 POI、换同类地点 |
| `poi_detail(ids)` | `/v5/place/detail` | id（最多 10 个用 `|` 分隔）, show_fields=business | 营业时间、人均 |
| `distance(origins, dest, mode)` | `/v3/distance` | origins（≤ 100）, destination, type | 粗排批量估时 |
| `route(mode, o, d, t)` | `/v5/direction/{driving,walking,bicycling,electrobike,transit/integrated}` | show_fields=cost；公交加 city1、city2 | 精排和推演的路段 |

实现要点：坐标统一 GCJ-02，保留 6 位小数；公交返回多条线路时取前 3 条，耗时最短作为均值，三条的差距用来估方差；路况（3.2）用驾车接口的 `cost.duration` 和上一次缓存值比较，涨幅 ≥ 20% 记一次"路况变化"。返回 `status != "1"` 时按 `infocode` 区分配额用完和参数错误，前者抛 `AMAP_QUOTA`。

### 6.2 和风天气

```python
import jwt, time   # PyJWT[crypto]，支持 EdDSA
def qweather_token():
    now = int(time.time())
    payload = {"sub": env.QW_PROJECT_ID, "iat": now - 30, "exp": now + 3600}
    return jwt.encode(payload, env.QW_PRIVATE_KEY, algorithm="EdDSA",
                      headers={"kid": env.QW_KEY_ID})
# 请求头：Authorization: Bearer <token>；域名用控制台里分配给你的 API Host
```

| 函数 | 接口 | 用途 |
|---|---|---|
| `hourly(lnglat)` | `/v7/weather/24h` | 出行时段每小时天气，S3 提前一天看 |
| `minutely(lnglat)` | `/v7/minutely/5m` | 未来 2 小时分钟级降水，判断"十分钟后下雨" |
| `warning(lnglat)` | 预警接口（路径以控制台文档为准） | 暴雨、大风预警 |

token 缓存 50 分钟。私钥用 `openssl genpkey -algorithm ED25519` 生成，公钥上传控制台，私钥只放服务器环境变量。

情境修正规则写在 `schema/context_rules.yaml`，例如：小时降水 ≥ 2 mm 时步行 ×1.15、骑行不可用、打车等车 +5 分钟；有暴雨预警时户外软活动价值减半。

### 6.3 限流和缓存

所有高德调用经过同一个 Redis 令牌桶（键 `rl:amap`，每秒补 3 个，容量 3），拿不到令牌就等，最多等 2 秒，超时按 `AMAP_FAIL` 处理。和风单独一个桶，每秒 5 个。缓存键和 TTL 见 2.6；路径缓存的键里带 15 分钟时段，同一时段内同一路段只查一次。

POI 和地理编码缓存可以提前预热：W1 把学校周边 3 km 的教学楼、食堂、地铁站、常去商圈跑一遍写进缓存，演示和试用时命中率高、速度快。

### 6.4 调用预算

高德个人开发者有每日配额和 QPS 上限（W1 在控制台"配额管理"里查实际数值，下文按每日 5000 次、QPS 3 估算）。

| 场景 | 每次消耗（未命中缓存时） | 说明 |
|---|---|---|
| 一次生成 | 约 27 次：搜索 6 + 详情 3 + 距离 3 + 路径 15 | 缓存命中后通常 10 次以内 |
| 一次录入解析（1.1） | 约 3–6 次：地理编码 + 每段路径 | |
| 一个计划的一天监控 | 约 30–60 次 | 每次 tick 只查"下一段"和"下下段"，路况不变就不重推演 |
| 一次重规划 | 约 5–12 次 | 换交通方式和换同类地点需要新路段 |

试用期按 30 名用户、人均每天 1 次生成加 1 个监控中的计划估算，每天约 30 × (15 + 45) ≈ 1800 次，在配额内。超过 80% 时 `monitor` 把 tick 间隔从 5 分钟放宽到 10 分钟，并在服务端日志告警。用户量再大就申请提升配额，不要靠多开 Key 绕过。

## 七 核心算法实现

代码在 `server/app/engine/`，纯 Python + NumPy，不依赖外部服务，可以单独测试。手机端不跑推演。画像只存在手机上（2.4），所以画像更新（本文 7.5）在手机上用 Kotlin 实现；服务端保留一份同样的 Python 实现供评测用，两边共用 `schema/testvectors/profile.json` 里的测试向量，保证算出来一样。

### 7.1 推演

每条边的耗时服从对数正态分布：`d = base × factor × ctx × exp(σ·z − σ²/2)`。`base` 是高德 ETA，`factor` 是画像系数，`ctx` 是情境修正，减 `σ²/2` 让均值等于 `base × factor × ctx`。公交另加等车时间，按指数分布，均值取画像里的 `bus_wait`。

```python
def simulate(g: PlanGraph, n=2000, seed=None) -> SimResult:
    rng = np.random.default_rng(seed)
    Z = rng.standard_normal((n, len(g.edges)))       # 公共随机数：比较候选方案时传入同一个 seed
    W = rng.exponential(1.0, (n, len(g.edges)))
    t = np.full(n, g.depart_ts)                       # 每个样本的当前时刻
    ok = np.ones(n, bool); per_node = {}
    for i, node in enumerate(g.topo_order()):
        e = g.in_edge(node)
        dur = e.base * e.factor * e.ctx * np.exp(e.sigma * Z[:, i] - e.sigma**2 / 2)
        if e.mode == "bus":
            dur += W[:, i] * e.wait_mean
        arrive = t + dur
        start = np.maximum(arrive, node.earliest)
        hit = start <= node.latest
        if node.hard:
            ok &= hit
        per_node[node.id] = stats(hit, node.latest - arrive)   # p_ok、slack 的 p10 和 p50、arrive_p90
        t = start + node.stay_sample(rng, n)
    return SimResult(p_all=ok.mean(), per_node=per_node,
                     weakest=min(per_node, key=lambda k: per_node[k].p_ok), seed=seed)
```

20 个节点、2000 个样本是 20 次长度 2000 的向量运算，单核 < 50 ms。验收用 `pytest-benchmark` 测，超过 50 ms 就把样本降到 1000，并在 SimResult 里记 `n_samples`。

### 7.2 出发时刻

"最晚几点出门还能有 90% 把握"用二分查找。出发时刻每提前 1 分钟，把握只会不变或变大，所以可以二分。

```python
def depart_by(g, target_p=0.9, lo=-120, hi=60, seed=42):
    # 以计划出发时刻为 0，单位分钟；在 [lo, hi] 里找满足 p ≥ target_p 的最晚时刻
    if simulate(g.shift_depart(lo), seed=seed).p_all < target_p:
        return None                         # 提前两小时也不够，交给方案搜索
    while hi - lo > 1:
        mid = (lo + hi) // 2
        if simulate(g.shift_depart(mid), seed=seed).p_all >= target_p: lo = mid
        else: hi = mid
    return lo                               # 约 8 次推演
```

固定 seed 保证同一输入每次结果一样，避免提醒时间来回跳。界面显示时取整到分钟，变化 < 3 分钟不提醒（8.3）。

### 7.3 方案搜索

```python
OPS = [change_mode, shift_time, drop_soft, swap_place, change_order, split_group]   # split_group 为 P1

def search(g, event, seed):
    base = simulate(g, seed=seed)
    cands = []
    for op in OPS:
        cands += op.enumerate(g, event)            # 每个算子只在"最薄弱环节及其后续节点"上展开
    cands += [c for c in llm_suggest(g, event) if valid(c)][:3]   # 大模型最多补 3 个，只能用这 6 种算子表达
    singles = [c for c in cands if feasible(c.apply(g))]
    pairs = [a + b for a, b in combinations(top(singles, 12), 2) if compatible(a, b)]
    opts = []
    for c in singles + pairs:
        g2 = c.apply(g); s = simulate(g2, seed=seed)
        opts.append(Option(ops=c, plan_after=g2, sim=s, cost=cost(g, g2, profile.weights)))
    front = pareto(opts, keys=[lambda o: -o.sim.p_all, lambda o: o.cost.total])
    return pick_diverse(front, k=3, by=lambda o: o.ops[0].kind)    # 主算子不同的 2–3 个
```

算子的展开范围要限住，不然组合会爆：`change_mode` 只试高德能给出的方式；`shift_time` 只试 ±5、±10、±15 分钟；`swap_place` 只在原地点 1.5 km 内找同类前 3 个；`change_order` 只对标了 `order` 的节点（如电影票、餐厅预约）生效，费用从节点的 `fee_rules` 读。单算子一般 15–30 个，加两两组合也在 150 个以内，150 × 50 ms ≈ 7.5 秒太慢，所以组合阶段推演降到 500 个样本，进入 Pareto 前沿的再用 2000 个样本复算。

代价公式按 v2 4.4：`w时间·时间损失 + w花费·额外花费 + w体力·(步行公里 + 换乘次数) + w社交·(他人等待人分钟 + 改约次数) + 放弃软活动价值`，权重从画像 `weights` 读。

### 7.4 最小放宽集（P1，对应 4.4 冲突解释）

所有方案都达不到门槛时，找出"最少放松哪几条软约束就能满足"。软约束最多 8 条，直接枚举 2⁸ = 256 个子集，按子集大小从小到大推演（每次 500 个样本），找到的第一层全部返回。最坏 256 × 15 ms ≈ 4 秒，放在异步任务里跑，界面先显示"××最多只有 y% 把握"。

### 7.5 画像更新

每段路走完记一条观测：`r = log(实际耗时 / 高德预计耗时)`，按"交通方式 × 是否高峰"分层（高峰定义见 2.4）。实际耗时来自三处，可信度从高到低：用户点"到了"、定位进入目的地 150 米内、复盘时用户手填。

```kotlin
// android/profile/BayesUpdater.kt
data class Factor(val mu: Double, val tau: Double, val n: Int)
const val MU0 = 0.0; const val TAU0 = 0.2; const val SIGMA = 0.15; const val N_CAP = 30

fun update(obs: List<Double>): Factor {          // obs 是该分层下未被排除的全部 r
    val recent = obs.takeLast(N_CAP)              // 只用最近 30 条，习惯变了能跟上
    val n = recent.size
    val tau2 = 1.0 / (1.0 / (TAU0 * TAU0) + n / (SIGMA * SIGMA))
    val mu = tau2 * (MU0 / (TAU0 * TAU0) + recent.sum() / (SIGMA * SIGMA))
    return Factor(mu, sqrt(tau2), n)
}
// 系数 = exp(mu)，可信区间 = exp(mu ± 1.96·tau)，画像页显示"你步行比导航慢 12%（8%–16%）"
```

`|r| > log 3`（实际是预计的 3 倍以上或三分之一以下）的观测不直接入库，复盘时问一句"这段是不是中途去办了别的事？"，用户选"是"就标 `excluded`。用户在画像页删掉某条观测或重置某个系数，都是重新跑一次 `update`，不需要撤销逻辑。

固定时长（出门准备、等车）用同样的方法更新，只是 r 换成 `实际分钟 − 默认分钟`，按正态共轭算。取舍偏好（6.4 功能，P1）记录用户每次在方案卡上选了哪个，P0 只存 `choice` 表，P1 再拟合权重。

### 7.6 冷启动

新用户没有观测时，所有系数为 1.0，固定时长用默认值（出门准备 10 分钟、公交等车 6 分钟、打车等车 5 分钟），推演用较大的 σ（见下表），所以第一次给出的把握会偏保守。

| 方式 | σ | 说明 |
|---|---|---|
| 步行 | 0.08 | |
| 骑行 | 0.10 | 含找车、停车 |
| 公交/地铁 | 0.20 | 另加等车时间 |
| 打车 | 0.18 | 另加等车时间 |

首次打开时问三个问题，答案直接写进先验，让第一次就有个人化效果：

1. "你走路比一般人快、差不多、还是慢？"——快、慢分别把步行 μ0 设为 −0.08、+0.10。
2. "说'五分钟出门'，一般要多久？"——选项 5 / 10 / 15 / 20 分钟，写入 `fixed_min.say5_actual`，也作为出门准备的初值。
3. "常用出行方式？"——多选，决定粗排时优先哪种方式。

答完写入画像，界面显示"已按你的回答调整，之后会根据实际出行继续校准"。

## 八 计划的生命周期

### 8.1 状态

| 状态 | 含义 | 存在哪 |
|---|---|---|
| DRAFT | 用户录入了但没确认 | 手机 Room |
| GENERATING | 一句话生成中，等 SSE | 手机 Room + 服务端 Redis 任务 |
| CANDIDATES | 2–3 套方案待选 | 手机 Room |
| DEPLOYED | 已选定并部署：日历已写、提醒已设 | 手机 Room |
| ACTIVE | 进入监控窗口（离第一个节点 ≤ 2 小时） | 手机 Room |
| REPLANNING | 发生变化，正在给方案卡 | 手机 Room |
| ENDED | 最后一个节点结束或用户点"结束" | 手机 Room |
| REVIEWED | 复盘卡已处理（填了或跳过） | 手机 Room |
| CANCELLED | 用户取消 | 手机 Room |

服务端不保存计划状态。每次调用都由手机把整份 PlanGraph 带上来，服务端算完返回。这样 P0 不需要账号和数据库，换手机或卸载重装，计划就没了，这一点在隐私说明里写清楚。

### 8.2 状态转移

```
DRAFT ──确认──▶ DEPLOYED
GENERATING ──done──▶ CANDIDATES ──选一套──▶ DEPLOYED
GENERATING ──error──▶ DRAFT（打开 1.1 表单）
DEPLOYED ──T−2h 闹钟──▶ ACTIVE
ACTIVE ──tick 返回 replan──▶ REPLANNING ──用户选了方案──▶ ACTIVE（新计划重新部署）
REPLANNING ──用户点"先不改"──▶ ACTIVE（30 分钟内同类变化不再提醒）
ACTIVE ──最后节点结束 + 30 分钟 / 用户点结束──▶ ENDED ──复盘──▶ REVIEWED
任意未结束状态 ──取消──▶ CANCELLED（删除日历条目和闹钟）
```

实现：`android/domain/PlanStateMachine.kt` 用一个 `sealed class Event` 加一个纯函数 `reduce(state, event): Pair<State, List<SideEffect>>`。副作用（写日历、设闹钟、发通知）由调用方执行，状态机本身可以单元测试。非法转移直接抛异常，测试覆盖所有边。

### 8.3 感知调度

手机端用 AlarmManager 定时唤醒，每次唤醒调一次 `POST /v1/tick`，带上计划和当前位置（用户授权了才带）。

| 时间段 | 间隔 | 查什么 |
|---|---|---|
| T−12h（只对 S3 短途） | 一次 | 天气逐小时预报、预警 |
| T−2h 到 T−30m | 15 分钟 | 天气、下一段路况 |
| T−30m 到出发 | 5 分钟 | 分钟级降水、下一段路况 |
| 途中 | 5 分钟，加上每到达一个节点 | 位置进度、下一段和下下段路况 |

tick 返回 `none`、`notify` 或 `replan` 三种决定。判定规则：

| 条件 | 决定 |
|---|---|
| p_all 降到 min(0.9, 部署时的 p_all − 0.05) 以下，或某个硬节点 p_ok < 0.8 | replan |
| 出发时刻变化 ≥ 3 分钟，但把握仍 ≥ 0.9 | notify（"建议 8:12 出门，比原来早 4 分钟"） |
| 其他 | none |

去重：同一计划、同一原因 10 分钟内只提醒一次。用户点了"先不改"，30 分钟内同类原因不再提醒，除非把握又降了 10 个百分点以上。

表里的间隔是目标值。手机息屏静止（Doze）时，系统限制同一个 App 的精确唤醒大约 9 分钟一次，所以 5 分钟的间隔可能变成 9 分钟。途中有定位前台服务在跑，不受这个限制。"该出门了"这一条提醒用 `setAlarmClock()`，它在 Doze 下也准点。各种唤醒方式的分工见 10.3。

### 8.4 通知

| 通知 | 渠道（NotificationChannel） | 优先级 | 按钮 |
|---|---|---|---|
| 该出门了 | `depart` | 高，带声音 | 出发了 / 晚 5 分钟 |
| 出发时刻变了 | `update` | 默认 | 查看 |
| 计划有风险（方案卡） | `risk` | 高 | 查看方案 |
| 途中倒计时（5.4 功能） | `ongoing` | 低，常驻 | 导航 / 到了 |
| 复盘 | `review` | 低 | 填一下 / 跳过 |

"出发了"按钮打开一个透明 Activity，由它启动定位前台服务。Android 12 起，App 在后台时不能直接启动前台服务；用户点通知按钮打开 Activity 后再启动，是系统允许的路径。

### 8.5 复盘

计划 ENDED 后 30 分钟（或用户当晚第一次打开 App）弹复盘卡。卡片最多问 3 个问题，按下面的顺序挑，问满 3 个就停：

1. 有 `|r| > log 3` 的异常观测时，先问"这段是不是中途去办了别的事？"（7.5）。
2. 没有自动拿到到达时间的节点，问"大概几点到的 ××？"，给预计时间前后 ±15 分钟的滑块。
3. 途中触发过方案卡的，问"这次的方案有用吗？"（有用 / 没用 / 没看）。
4. 出门准备时长偏差最大的那次，问"今天出门准备用了多久？"。

提交后在手机上跑 7.5 的更新，复盘卡底部显示变化："你下雨天骑车比导航慢 18%，下次会提前 4 分钟提醒你"。这句话的数字来自更新前后的系数差，文字用固定模板，不调大模型。跳过复盘也行，已经自动记录的观测照样入库。

## 九 端到端时序

### 9.1 S1 赶课（录入 + 应变）

1. 晚上用户说"明早 8 点三教上课，宿舍出发，骑车"。手机调 `parse`，服务端大模型解析，高德算路段，推演给出"7:38 前出门有 92% 把握"，用户确认，状态 DEPLOYED。
2. 部署：写日历条目（标题带 `[随变:planId]`）、设 6:00 的 T−2h 闹钟、设 7:38 的 `setAlarmClock`。
3. 早上 7:15 tick：分钟级降水显示 7:40 起有雨。服务端按情境规则把骑行判为不可用，推演 p_all 降到 0.61，返回 replan，附两张方案卡：步行 7:31 出门（91%）、公交 7:34 出门（88%）。
4. 用户选步行。手机更新计划、改闹钟到 7:31、改日历，操作日志记三条。通知显示"已改为步行，7:31 出门"。
5. 7:31 用户点"出发了"，前台服务开始定位，常驻通知倒计时。7:56 进入三教 150 米内，记到达观测。
6. 到达节点结束 30 分钟后弹复盘卡，提交后更新"步行|高峰"系数。

### 9.2 S2 聚会（朋友迟到）

1. 用户说"周六晚 6 点和三个同学在五道口吃火锅，人均 100 以内"。走一句话生成流水线（第四节），SSE 依次推送进度，15 秒内出三套：稳妥（离地铁口近的店，17:20 出门）、紧凑（评分更高的店，饭后加一个桌游店）、省钱（团购套餐店）。
2. 用户选稳妥，一键部署：日历、闹钟、给群里的消息草稿（预览后确认，复制到剪贴板再打开微信）。
3. 17:50 用户在群里收到"我堵车了，大概晚 25 分钟"，在 App 里说"小王晚 25 分钟"。手机调 `report`，大模型把这句话解析成事件 `{who: 同学A, delay_min: 25}`。
4. 服务端推演：餐厅订位 18:15 过号（硬约束，来自 1.1 录入的"订了位"），p_ok 跌到 0.4，返回三张方案卡：先到的人入座点菜（保住订位）、改约 18:30 打电话给店家（只跳转拨号）、换到不需要订位的隔壁店。
5. 用户选第一张，App 生成一条群消息草稿"我们先进去点菜，你到了直接来 3 号桌"，用户预览后自己发。
6. 复盘时问"这次的方案有用吗？"。

### 9.3 S3 一日短途（生成 + 天气重排）

1. 周四用户说"周六去颐和园玩一天，下午想去个咖啡馆，别太累"。生成三套计划，"别太累"被解析成软约束 `walk_total ≤ 8 km`，骑行被排除。
2. 选紧凑，部署：日历写 4 个条目、周五晚 20:00 设 T−12h 检查。
3. 周五晚检查：和风逐小时预报周六 13–16 点中雨。按情境规则户外节点价值减半，推演把"下午游西堤"判为高风险，返回方案卡：把西堤挪到上午、咖啡馆挪到下午（时间平移 + 换序），把握从 0.64 回到 0.88。
4. 用户确认，手机批量改日历（一键确认，一次授权 4 条），操作日志记录每一条改动和原值，可一键撤销。
5. 当天按 8.3 正常监控。晚上复盘，更新"步行|非高峰"系数；"别太累"对应的步行上限记进 choice 表，P1 的取舍偏好（6.4）再用。

这三条时序就是演示视频的脚本骨架，也是第 5 周端到端联调的验收用例。

| 授权中心 / 操作日志 | 7.3、7.4 | 每个权限的用途和最近使用时间；日志按计划分组，可撤销 |
| 截图导入 | 1.2 | 系统图片选择器（`PickVisualMedia`，不需要存储权限）→ OCR → 字段确认 |

### 10.3 后台唤醒和保活（国行手机，没有谷歌服务）

v2 1.8 写的是"WorkManager 定时检查"。落地时改成下面的分工，因为 WorkManager 最短周期 15 分钟且不保证准点，满足不了 8.3 的 5 分钟间隔。

| 任务 | 用什么 | 说明 |
|---|---|---|
| "该出门了"提醒 | `AlarmManager.setAlarmClock()` | 系统当作闹钟处理，Doze 下也准点，状态栏会显示闹钟图标 |
| T−2h 进入 ACTIVE、监控期 tick | `setExactAndAllowWhileIdle()` | 每次触发时先调 tick，再根据 8.3 的表设下一次 |

精确闹钟权限：上面两种调用在 Android 12 起都要权限。清单里同时声明 `USE_EXACT_ALARM`（Android 13 起安装即授予，适用于提醒类 App；本作品不走谷歌商店，不受它的上架政策限制）和 `SCHEDULE_EXACT_ALARM`（加 `android:maxSdkVersion="32"`，给 Android 12 用）。每次设闹钟前调 `canScheduleExactAlarms()`，返回 false 就跳设置页（`ACTION_REQUEST_SCHEDULE_EXACT_ALARM`）；用户不给就降级为 `setWindow()`（10 分钟窗口，不需要权限），界面提示"提醒可能晚几分钟"。上架 OPPO 软件商店前，在开发者后台确认它对这个权限的审核要求。

| 任务 | 用什么 | 说明 |
|---|---|---|
| 途中定位 | 前台服务，`foregroundServiceType="location"` | 只在用户点"出发了"后启动，到最后一个节点或 3 小时后自动停 |
| 复盘卡、清理旧数据、缓存预热 | WorkManager | 不要求准点的事 |
| 开机、改时间、App 升级后恢复闹钟 | `BOOT_COMPLETED`、`TIME_SET`、`MY_PACKAGE_REPLACED` 广播 | 从 Room 读出所有 DEPLOYED/ACTIVE 计划重新设闹钟 |

闹钟触发后要联网调 tick，在 `BroadcastReceiver` 里用 `goAsync()` 加协程，超时 8 秒。超时就用上次的推演结果，不阻塞。

ColorOS 等国产系统会清理后台。首次部署计划时弹一次引导："为了按时提醒，请允许随变后台运行"，按钮跳到电池优化设置（`ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`，失败就跳应用详情页）。引导页配 OPPO 手机的截图。被清理后闹钟依然由系统保管，`setAlarmClock` 的出门提醒不受影响，最坏情况是 tick 少几次。OPPO 推送（P1）可以作为补充唤醒通道，P0 不依赖它。

验收：在测试机上锁屏放置 2 小时，出门提醒误差 ≤ 1 分钟，tick 实际次数 ≥ 计划次数的 60%。这个数写进测试报告。

### 10.4 执行器

每个执行器实现同一个接口 `interface Executor { val type: ActionType; suspend fun run(a: Action): ExecResult; suspend fun undo(log: ActionLog): Boolean }`，只能经 `ActionGateway`（第十二节）调用。

| 动作 | 实现 | 撤销 |
|---|---|---|
| 写/改/删日历 | `CalendarContract`。首次使用时建一个本地日历"随变"（`ACCOUNT_TYPE_LOCAL`，用 sync adapter 方式插入 Calendars 表），所有条目写进这个日历，描述末尾带 `[随变:planId]` | 日志里存 event_id 和改动前的字段，撤销时写回或删除 |
| 读日历（1.3） | 查询 `Instances` 表，只取今天起 7 天，只读标题、时间、地点 | 只读，无需撤销 |
| 导航 | `amapuri://route/plan/?dlat=..&dlon=..&dname=..&dev=0&t=..`（t：0 驾车、1 公交、2 步行、3 骑行；dev=0 表示坐标已是高德坐标系）。没装高德就打开 `https://uri.amap.com/navigation?to=lng,lat,名称&mode=bus&coordinate=gaode&callnative=1` | 不需要 |
| 打车 | 打开高德路线页（t=0），用户在高德里选打车；或者用 `getLaunchIntentForPackage` 打开已安装的打车 App。不传订单参数，不承诺直接下单 | 不需要 |
| 短信草稿 | `Intent(ACTION_SENDTO, Uri.parse("smsto:号码")).putExtra("sms_body", 草稿)`，打开系统短信界面，由用户点发送。号码由用户用系统联系人选择器（`ACTION_PICK` + `Phone.CONTENT_URI`）选，不需要通讯录权限 | 不需要 |
| 微信草稿 | 草稿写入剪贴板，Toast 提示"已复制，粘贴到群里"，再 `getLaunchIntentForPackage("com.tencent.mm")` 打开微信 | 不需要 |
| 拨号 | `ACTION_DIAL`，只把号码填进拨号盘，不需要电话权限 | 不需要 |
| 改签/退订/预约 | 打开订单里记的链接或对应 App 首页（只跳转，5.6 功能 P1） | 不需要 |
| 截图 OCR（1.2） | `TextRecognition.getClient(ChineseTextRecognizerOptions.Builder().build())`，图片在端上识别，只把识别出的文字发给 `/v1/ocr/parse` | 不需要 |

Android 11 起要在清单 `<queries>` 里声明会查询的包：`com.autonavi.minimap`、`com.tencent.mm`，以及打车 App 的包名，否则 `getLaunchIntentForPackage` 返回 null。

## 十二 动作关卡 ActionGateway

所有对外动作都经过这一个入口，这是"可信可控"（v2 第五节）在代码里的落点。

### 12.1 唯一来源 `schema/actions.yaml`

```yaml
- {type: plan_update,      tier: auto,      undo: true}
- {type: alarm_set,        tier: auto,      undo: true}
- {type: calendar_write,   tier: one_tap,   undo: true,  grant: WRITE_CALENDAR}
- {type: navigate,         tier: one_tap,   undo: false}
- {type: taxi_open,        tier: one_tap,   undo: false}
- {type: msg_draft_sms,    tier: preview,   undo: false}
- {type: msg_draft_wechat, tier: preview,   undo: false}
- {type: location_share,   tier: preview,   undo: true}   # P1
- {type: h5_sync,          tier: preview,   undo: true}   # P1
- {type: order_jump,       tier: jump_only, undo: false}
- {type: dial,             tier: jump_only, undo: false}
```

`tier` 的四个取值对应 v2 5.2：`auto` 自动、`one_tap` 一键确认、`preview` 预览后确认、`jump_only` 只跳转。Gradle 构建时用一个小任务把它生成 Kotlin 的 `enum class ActionType(val tier: Tier, val undoable: Boolean)`，计划书里的动作分级表也由脚本从这份文件生成。

### 12.2 一个动作的执行流程

所有执行器只能由 `ActionGateway.submit(action)` 调用，执行器类本身是 `internal`，界面层拿不到。流程如下：

1. **白名单检查。** `action.type` 不在 `ActionType` 枚举里就丢弃，`action_log.decision` 记 `rejected_unknown`。服务端传来的方案里只有算子，不会有动作；动作是手机端按用户选中的方案卡在本地组装的。
2. **自主等级检查。** 读这条计划的 `autonomy`：
   - L0 只提醒：除 `plan_update` 外一律不执行，只发通知。
   - L1 给方案：显示方案卡和"去操作"说明，不调起任何执行器。
   - L2 确认后执行（默认）：按 `tier` 走第 3 步。
   - L3（P1）：`auto` 和"只影响自己、可撤销"的 `one_tap` 动作（目前只有 `calendar_write`）直接执行，做完发通知。
3. **按 tier 确认。** `auto` 直接执行；`one_tap` 弹底部确认条，列出"要做什么、改哪条日历"；`preview` 弹全屏预览，正文可编辑、接收人可改，按钮写"去短信发送"或"复制并打开微信"，不写"发送"；`jump_only` 只显示"将打开 xx 页面"。
4. **授权检查。** 有 `grant` 字段的动作，先查系统权限，没有就走 10.5 的说明页再申请；用户拒绝则记 `denied`，方案卡上标"需要日历权限"。
5. **写日志再执行。** 先写一条 `action_log`（`decision=confirmed`，`evidence_json` 存当时依据面板的内容），再调执行器，结果回写同一条记录（`done` 或 `failed` 加原因）。
6. **撤销。** `undo=true` 的动作在操作日志里显示"撤销"按钮，调用 `Executor.undo(log)`，成功后再写一条 `undone` 记录。一次采纳方案产生的多个动作共用一个 `batch_id`，可以一键整批撤销（9.3 的批量改日历就是这样）。

一次"采纳方案"在代码里就是：用户点方案卡 → 本地生成动作列表 → 逐个 `submit` → 全部写进同一批日志。演示"可信可控"时，打开授权中心和操作日志就能把这条链路完整展示出来。

### 12.3 代码里不存在的能力

v2 5.2 的最后一行"代码里不存在"靠 CI 保证，不靠自觉。`scripts/forbidden_scan.sh` 在每次提交时检查以下内容，命中任意一条构建失败：

| 检查 | 命中内容 | 对应承诺 |
|---|---|---|
| 源码 grep | `SmsManager`、`sendTextMessage`、`sendMultipartTextMessage` | 不自动发短信 |
| 源码 grep | `AccessibilityService`、`performGlobalAction`、`dispatchGesture` | 不模拟点击、不替用户在别的 App 里操作 |
| 依赖检查 | 支付 SDK 包名（`com.alipay`、`com.tencent.mm.opensdk` 中的支付类、银联） | 不自动支付 |
| Manifest 检查 | `READ_CONTACTS`、`READ_SMS`、`SEND_SMS`、`SYSTEM_ALERT_WINDOW`、`ACCESS_BACKGROUND_LOCATION`、`BIND_ACCESSIBILITY_SERVICE` | 和 10.5 的不申请清单一致 |
| 服务端 grep | 请求体里出现 `chat_text`、`notification_raw` 字段 | 不上传聊天全文和通知原文 |

微信只用 `getLaunchIntentForPackage` 打开，不接入微信开放平台 SDK，所以也不存在"替用户分享"的接口。扫描脚本和结果截图放进计划书，评委可以自己跑。

### 13.2 性质测试（hypothesis）

随机生成计划图（3–8 个节点、随机方式和时间窗）跑下面四条，每条 200 个例子：

1. `0 ≤ p ≤ 1`，对 p_all 和每个 p_ok 都成立。
2. 同一输入、同一 seed，两次 `simulate` 结果完全相同。
3. 出发越早把握越大：`simulate(g.shift_depart(a)).p_all ≥ simulate(g.shift_depart(b)).p_all`，a < b，同一 seed。这是 7.2 二分查找成立的前提。
4. 方案搜索输出里的每个方案，`plan_after` 在推演里的 p_all 和方案卡上显示的一致（复算误差 < 0.02）。

### 13.3 回放评测 `eval/run_replay.py`

每条回放样本一个 JSON：`{id, source: real|synthetic, plan, events:[{t, kind, data}], label:{affected:[node_id], feasible_options:[...], outcome: ok|late}}`。外部接口返回值也录在样本里（`recorded_api`），运行时用假网关回放，**不联网、结果可复现**。

运行器对每条样本按时间顺序喂事件，调用和线上同一份 `engine.search`，输出 v2 8.1 的指标：影响识别 F1、方案可行率、Brier 分数和校准曲线（10 档）、感知延迟。真实和合成分开统计。对照组 `baselines/fixed_rule.py` 是"提前 N 分钟出门"，N 取 10/15/20 分别报。

### 13.4 生成评测 `eval/run_generate.py`

生成测试集每条是 `{sentence, city, now, label:{must:[...], must_not:[...]}}`。对每句话跑 `/v1/generate`，检查每套计划的：营业时间是否覆盖到达时刻、预约时段是否对得上、路程是否用高德复算后仍成立、地点是否真实存在（POI id 能查回）。对照组 `baselines/pure_llm.py` 用同一个模型、同一句话，让大模型直接写行程，再用同一套检查算可行率、地点不存在率和时间错误率。多样性指标按 v2 8.1 算。生成评测要调真实高德，所以只在手动触发和每晚定时跑，结果存档到 `eval/reports/日期.json`。

### 13.5 CI（GitHub Actions）

| 工作流 | 触发 | 内容 | 失败条件 |
|---|---|---|---|
| `server.yml` | 每次推送 | ruff、pytest（13.1、13.2）、`pytest-benchmark` | 测试失败；单次推演 > 50 ms |
| `android.yml` | 每次推送 | ktlint、单元测试、`assembleDebug`、生成 ActionType 枚举 | 测试或构建失败 |

### 13.6 体验对比和试用的埋点

v2 8.2 的操作成本对比由 D 主持：同一名同学先手动完成任务（自己查地图、看天气、写日历、发消息），再用随变完成，录屏计时。随变这边的点击次数和切换 App 次数直接从埋点读，不靠人数。

埋点只记事件名和时间，不记内容，存在手机 Room 的 `metrics` 表，用户在设置页点"上传匿名统计"才发给 `POST /v1/metrics`（P0 可以只导出成文件发给 D）。事件包括：`plan_created{source: parse|ocr|generate}`、`candidates_shown{n}`、`candidate_picked{style}`、`deployed{actions_n}`、`tick_notify`、`replan_shown{trigger}`、`option_picked{rank}`、`replan_dismissed`、`action_undone`、`review_done{skipped}`。v2 8.3 的采纳率 = `option_picked / replan_shown`，误报率 = `replan_dismissed / replan_shown`（再由访谈确认哪些是真误报）。

## 十四 部署与上线

### 14.1 服务器怎么选

**初赛阶段用香港地区的轻量云服务器（2 核 4G 即可），不用做 ICP 备案。** 内地服务器用域名对外提供 HTTPS 必须先备案，一般要 1–3 周，会卡住 W2 的联调。香港服务器访问高德、和风、百炼、DeepSeek 都没有问题，手机访问延迟多几十毫秒，对本作品无影响。

DAILY_LLM_CALLS_MAX=3000                  # 全站每日大模型调用上限，超了直接走兜底
```

### 14.3 防滥用和自检

服务端接口没有账号，必须防止别人拿去白嫖大模型额度：按设备 ID 每分钟 20 次（第三节开头已定），按 IP 每分钟 60 次，全站每日调用上限 `DAILY_LLM_CALLS_MAX`。手机请求里带 `X-App-Version`，版本太旧返回 426 提示更新。

`GET /v1/health` 依次探测大模型（主备各发一个 1 token 请求）、高德（地理编码一个固定地址）、和风（查一次实况）、Redis，返回每项的状态和耗时。演示和答辩前 10 分钟必须打一次。日志用 JSON 格式输出到标准输出，只记接口名、耗时、错误码和脱敏后的文本，保留 7 天。

### 14.4 APK 签名和分发

正式签名的 keystore 由 A 生成，**不进仓库**，base64 后放 GitHub Secrets，`android.yml` 在打 tag 时用它打 `assembleRelease` 并上传到 GitHub Releases。keystore 本身另存两份离线备份，丢了就没法覆盖安装旧版本。

试用期分发：Releases 下载链接做成二维码；App 内"检查更新"读 `GET /v1/version`。提交作品时交 release APK，并在说明里写清最低 Android 版本（8.0）和首次启动要授的权限。上架 OPPO 软件商店不是 P0 要求，要上架时再做 App 备案和隐私合规检测（P2）。

### 和 Claude/Codex 协作的规矩

仓库根目录放 `AGENTS.md`（Codex 读）和 `CLAUDE.md`（Claude 读），两份内容一样，写下面这些规则：

1. 一次只做一个模块。给它的上下文是 `schema/` 里相关的 JSON Schema、本文档对应的那一节、要改的文件，不要把整个仓库丢给它。
2. 先写测试再写实现。先让它按第十三节的表写测试，人看一遍测试是否符合本文档，再让它写实现直到测试通过。
3. `schema/`、`actions.yaml`、`.env.example` 只能人改。它想改这些文件时，要先说明理由，人确认后再动。
4. 不许在代码里写死模型名、API Key、城市名；模型名只从 `.env` 读。
5. 不许调用 12.3 列出的禁用接口；`forbidden_scan.sh` 不过就不能合并。
6. 界面上出现的每一个概率、时间、距离都来自引擎或高德返回值，不许让大模型生成数字（5.4 的校验会拦）。
7. 每次说"完成了"，必须贴出它实际运行的测试命令和输出，没跑过的不算完成。

另外三条是人自己要守的。后台、闹钟、通知、权限相关的代码，AI 写完后必须在真机上验证（至少一台 ColorOS、一台其他品牌），模拟器上能跑不算数。用 AI 批量生成的回放样本，`source` 一律标 `synthetic`，计划书里真实和合成分开报。每周日验收时，对照本周表格逐项勾，没通过的项写进下周一的对齐会。
