# 乙：JSON 分层契约与交互协作草案

评审日期：2026-11-28。工作分支：`feature/server-w2-parse`。

本文是设计评审材料，不代表接口已经实现或已经变更。现有 `schema/`、接口示例和 Android 源码均未修改。状态区分为「现有」「提案」「内部」；提案经双方确认后才进入共用契约。P0 表示乙本轮核心链路，P1 表示需要甲乙配合的体验增强，并非自动追加开发承诺。

## 1. 已核对的基础

- `POST /v1/parse` 当前仍返回固定示例；公开响应是 `intent`、`draft_plan`、`questions`。
- `intent.schema.json` 禁止额外字段，活动目前只有 `text/category/keyword`，不能直接塞入新的时间结构。
- `plan_graph.schema.json` 的边要求 `id/from/to/mode/eta_min`；缺路程时不能用零填充未知值。
- `simulate` 对完整计划调用真实引擎；`replan` 当前仅处理指定边的延误，尚非通用方案搜索。
- 甲的 `ParseResponse` 接受空 `draft_plan`，并能显示 `questions`；这不等于已经支持结构化选项、地图回填或自动打开表单。
- `HomeScreen.kt` 目前是纵向滚动页面：标题及服务状态、输入框、录入按钮、提示、计划卡、已保存计划。输入使用 `rememberSaveable`，尚不能据此认定具有持久草稿恢复。
- Android 当前没有启用定位权限；地图附近查询和标签管理尚未实现。

## 2. 时间取得、语义和约束

### 2.1 单一取时入口

甲端内部通过一个 `TimeReference.snapshot()` 取得时间快照；界面不直接处理重试、网络时延或偏差。乙可提供只读取时接口，拟为 `GET /v1/time`，返回 `server_time` 和 `timezone`。这是新增提案，不复用健康检查，也不改变已有业务响应包裹结构。

| 场景 | 建议行为 |
|---|---|
| 打开应用 | 立即读取系统时间用于显示，同时后台尝试网络取时 |
| 开始一轮规划 | 主动获取时间参考；第一次最多 1.5 秒，失败后等待至多 0.2 秒并重试一次，总预算 3.2 秒 |
| 网络仍失败 | 使用本地系统时间；内部记录本次未取得网络参考，不冒称已经联网校准 |
| 同一轮模型重试、追问续填 | 使用原来的日期锚点；不能重新解释“明天” |
| 用户明确开始新计划 | 获取新的时间快照 |
| 采纳或执行计划前 | 读取当前时间检查是否过期；不得顺便平移原计划日期 |

所有耗时和重试截止用单调时钟测量，不能用可能被校正的墙上时钟计时。网络时间只通过可信 HTTPS 服务取得；服务端时钟由系统授时维护。服务端返回时间不自动等于已验证的高精度授时结果。保存网络往返耗时和检查时刻，拒绝明显异常的参考值；不能据此擅自修改手机系统时钟。

### 2.2 自然语言时间的确定规则

以下是拟定的解释规则，须通过真实语料验证；不依靠大模型自行猜日期。模型抽取原词和语义，确定性的日期运算在代码里完成。示例锚点为 `2026-11-28`（周六），计划时区为 `Asia/Shanghai`，一周从周一开始。

| 输入 | 参照 | 示例结果或处理 |
|---|---|---|
| 昨天／明天／后天 | 本轮固定的当地日期 | 11 月 27 日／29 日／30 日 |
| 次日／第二天 | 前文明确指向的事件日期 | 前文为 12 月 5 日，则为 12 月 6 日；缺失或多个参照时追问 |
| 这周三／本周三 | 锚点所在自然周 | 11 月 25 日；如果已经过去，询问是否改为下周，不自行更改 |
| 这周日／本周天／本周星期日 | 同一自然周；日、天均表示周日 | 11 月 29 日 |
| 周三／周日 | 缺少周限定时结合上下文形成候选 | 先展示具体年月日；已有日期冲突或存在多种合理解释时追问 |
| 下周三／下周日 | 锚点的下一自然周 | 12 月 2 日／6 日 |
| 明早八点 | 日期为明天，时间为 08:00 | 仍须确定“出发／到达／预约”的用途 |
| 八点 | 上下午和用途可能缺失 | 已有明确上下文则继承；否则只追问缺失项 |

区分理解与执行：历史时间可以被正确理解，但不能因此安排过去的出门动作；多日表达也可以识别，超出当前单日能力时明确说明。复用草稿时保留原词、已解析日期及参照，跨午夜不自动重算。

### 2.3 时间语义先于计划字段

内部时间条目建议包含：`raw_text`、`reference_date`、`resolved_date`、`time`、`relation`、`confirmation`。

- `relation` 区分 `depart_at`、`arrive_by`、`start_at`。
- `confirmation` 区分尚有歧义、语义明确但未确认、用户已确认；模型输出不能自称用户已确认。
- `08:00` 的含义必须确定后，才能映射到既有 `window` 或 `constraints`。
- 现有 `arrive_by` 约束可直接表达最晚到达；固定预约开始时间可用节点时间窗表达。
- 用户指定出发时间不等于引擎建议的最晚出发时间；前者需明确保存位置和对应请求字段，不能静默覆盖成 `depart_by`。
- 内部结构不添加到目前禁止额外字段的 `intent`；若需要跨端传送，应走公开契约评审。

## 3. 交互位置与草稿恢复

| 目标 | 对照当前界面的建议位置 | 约束与负责方 |
|---|---|---|
| 首次引导 | 输入框附近的轻量说明，按顺序介绍输入、核对、确认 | 可跳过；甲端保存引导版本。不开屏强索定位权限 |
| 再次查看教程 | 标题右侧新增“使用帮助”入口 | 不依赖设置页已存在；甲端负责 |
| 输入帮助 | 现有“说一句话”框下放一条示例和可点击范例 | 例：“明早从宿舍骑车，8 点前到三教”；不能强制用户背格式 |
| 结果核对 | 输入框下、计划卡前放已识别条件和待补充项 | 日期显示具体年月日；只编辑缺失或冲突项 |
| 同名地点选择 | 紧凑屏在输入区下方展开候选列表；宽屏可用侧栏 | 候选显示名称、区域、地址和可用的距离依据，不能直接选择第一项 |
| 候选过多 | 从紧凑列表展开到全屏地点选择，再返回原草稿 | 侧栏/底栏都可能遮挡内容，必须让布局适配、可滚动，检查键盘和大字体 |
| GPS 入口 | 起点旁的“使用当前位置”按钮 | 用户点击时再申请前台定位权限；拒绝后保留手动输入 |
| 地点标签 | 地点详情旁的编辑入口 | 标题、颜色、描述即可；颜色不能成为唯一识别依据 |

引导绑定 Compose 组件的语义标识与实际布局位置，不使用固定屏幕坐标。验证范围包括小屏、横屏、字体放大、键盘弹出和 TalkBack。本文没有测量设备屏幕，也没有声称已有以上入口。

草稿分层缓存：

1. 甲端本地保存原始输入、确认过的条件、待回答问题和选择中的地点；退出再进入时能恢复。
2. 相对日期保存解析时的参照和结果。跨午夜或结果已过期时提示用户复核，不直接改成另一日。
3. 路线和天气独立失效：草稿还在不代表外部数据还有效。起终点、方式、日期/时段或坐标系变化时重查受影响路段。
4. 仅改标题、颜色、描述不重查路线，也不重新调用模型；定位轻微变化不自动启动附近搜索。
5. 上一次请求晚返回时，必须核对本地草稿版本；旧结果不能覆盖较新的用户修改。

## 4. 地图、定位与标签

- 位置来源要明确，包括坐标系、精度和取得时间；GPS/WGS-84 坐标不能直接当成高德 GCJ-02。坐标转换集中在地图适配逻辑中，避免多处重复转换。
- “附近”可先使用本地收藏和已核验地点目录。在线附近查询由用户显式触发，受缓存和搜索预算控制。
- 搜索结果的距离排序不等于热度，缺少可核验的热度来源时只称“附近地点”，不标“热门”。
- 当前乙任务明确禁止 parse 调用 `/v5/place/*`；附近搜索是独立的后续协作入口，不暗中并入本轮 parse。
- 近似位置可以帮助确定区域，不能直接假装已经取得精确路线起点。路线查询前让用户确认地点。
- 自定义标签仅是本地组织信息，不能改变活动是否必做、时间约束或推演权重；不放进 `PlanGraph.category`。
- 路线失败分为起终点未确定、指定方式无路线、上游暂时不可用、配额不足。只给相应的补救操作；未经用户同意不自动换交通方式。

## 5. 分层、优先级 JSON 数据结构表

表内路径采用字段路径表示法。不同接口的 JSON 不强制装入统一大包，避免破坏当前 Android 和引擎契约。

| 层 | 优先级 | 对象与关键字段 | 类型与语义 | 产生方 → 消费方 | 当前状态与校验重点 |
|---|---|---|---|---|---|
| L0 交互恢复 | P1 | `LocalDraft.id/version/input/confirmed_fields/pending_fields` | 草稿标识、编辑版本、原输入、已确认/待补充内容 | Android → Android | 提案；持久化、跨午夜复核、旧响应不可覆盖新编辑 |
| L0 交互恢复 | P1 | `LocalGuide.version/completed` | 教程版本与是否看过 | Android → Android | 提案；可跳过和重新打开，不上传服务端 |
| L0 交互恢复 | P1 | `PlaceLabel.id/title/color/description`、`PlaceRef.label_ids` | 标签标题、颜色、说明；地点引用标签 ID | Android → Android | 提案；不进入算法类别，删除标签不删除地点 |
| L1 时间参考 | P0 | `/v1/time → server_time/timezone` | 带偏移时间字符串、IANA 时区 | 乙 → 甲 | 提案；只读、有超时和一次重试，不宣称修改系统时钟 |
| L1 请求输入 | P0 | `parse.text/now/city_adcode` | 原话、固定时间锚点、城市编码 | 甲 → 乙 | 现有输入约定；真实校验尚待实现。`now` 不是可信的任意服务端计费时间 |
| L1 请求输入 | P0/P1 | `parse.timezone`、可选位置 `location.lng/lat/crs/accuracy_m/captured_at` | 明确时区；经纬度、坐标系、精度、取样时间 | 甲 → 乙 | 提案；当前接口文档提过 `loc?`，没有已冻结的这套位置结构，不能直接发送 |
| L2 意图抽取 | P0 | `intent.date/date_fuzzy/origin/members/must/prefs/questions/unsupported` | 已有意图结构，活动为 `text/category/keyword` | 模型 → 乙 → 甲 | 现有 Schema；额外字段禁止。类型合法不代表事实正确 |
| L2 时间规范化 | P0 | `ResolvedTime.raw_text/reference_date/resolved_date/time/relation/confirmation` | 原词、参照、具体日期时间、用途、确认状态 | 乙内部 | 内部提案；确定性日期计算；不允许模型伪造“已确认” |
| L2 地点确认 | P1 | `PlaceChoice.id/name/address/location` | 地点候选标识、名称、地址、坐标依据 | 地图 → 乙 → 甲 | 提案；用户选择与草稿版本关联；候选列表不得放进 `questions:string[]` |
| L3 可推演计划 | P0 | `draft_plan.plan_id/version/date/status/p_target/members` | 计划标识、版本、日期、生命周期、目标把握、成员 | 乙 → 甲及引擎 | 现有 Schema；版本为正整数，目标值在 0–1；日期不能跨阶段漂移 |
| L3 可推演计划 | P0 | `draft_plan.nodes[].id/kind/name/loc/window/duration/hard` | 节点、GCJ-02 坐标、时间窗、停留分钟、硬条件 | 乙 → 甲及引擎 | 现有 Schema；ID 唯一、经纬度有效、时间含义确定；未知坐标省略 |
| L3 可推演计划 | P0 | `draft_plan.edges[].id/from/to/mode/eta_min/dist_m/src` | 路段、现存节点引用、方式、分钟、米、来源 | 地图及乙 → 甲及引擎 | 现有 Schema；禁止用零表示未知 ETA；验图、方式和取数适用时间 |
| L3 可推演计划 | P0 | `draft_plan.constraints[].id/type/node/time/hard` | 约束类型、作用节点、时间、是否硬约束 | 乙 → 引擎及甲 | 现有 Schema；目标节点存在，不能混淆到达和开始约束 |
| L3 来源依据 | P0 | `nodes/edges[].src.tag/fetched_at` | 数据来源及获取时刻 | 乙 → 甲 | 现有 Schema 仅允许这两个字段；现有结构不足以表达完整有效期/坐标来源 |
| L3 来源依据 | P0 | 内部 `Evidence.field/provider/captured_at/valid_until/context` | 字段来源、有效期、适用路线和时段 | 乙内部 | 内部提案；若要公开扩展，应放独立经过评审的依据结构，不能直接扩充 `src` |
| L4 解析结果 | P0 | `intent/draft_plan/questions` | 意图、可推演计划或无计划、兼容的文字提示 | 乙 → 甲 | 现有成功结构；`draft_plan:null` 的失败语义是提案，甲类型可接收仍需契约测试 |
| L4 解析状态 | P0 | `state/reason_code` | `ready/needs_input/unavailable`；机器可读原因 | 乙 → 甲 | 新增提案；`PlanGraph.status` 仍表示生命周期，不能替代本次解析状态 |
| L4 补充交互 | P1 | `clarifications[].id/field/message/options` | 问题 ID、目标字段、文案、结构化选项 | 乙 → 甲 | 新增提案；保留原 `questions:string[]`，不直接把字符串换对象 |
| L4 推演结果 | P0 | `sim.p_all/per_node/weakest/depart_by` | 把握、节点结果、最弱环节、最晚出发 | 引擎 → 甲 | 现有运行接口；`per_node` 为列表，实际节点时间当前为分钟数，不盲信旧示例格式 |
| L4 刷新结果 | P0 | `plan_patch/changed/weather` | 路段补丁、变化项、天气 | 乙 → 甲 | 现有示例；真实刷新未实现。`weather.bike_available` 为任务书要求的新增项 |
| L4 重算结果 | P0 | `base_version/before/after/affected/options/relax` | 基础版本、前后结果、影响、备选 | 引擎及乙 → 甲 | 现有运行接口；只把结果应用到对应计划版本；不把旧示例当成现有算子搜索 |

P0/P1 混合行中，明确时区属于 P0 时间语义，定位字段属于 P1 协作扩展。草稿缓存可先由甲端内部实现，不强迫乙维护用户会话或收集完整草稿。需要跨请求标识和版本回显时，另行确定最小字段，不能假设本地版本可自动完成服务端幂等。

### 5.1 状态约束

| 解析状态（提案） | `draft_plan` | `questions` | 可以继续的操作 |
|---|---|---|---|
| `ready` | 完整且通过结构、语义、来源校验的计划 | 可以为空 | 展示、保存计划；部署仍需独立确认与有效性检查 |
| `needs_input` | `null` | 明确缺失项或歧义 | 保存本地输入草稿、补充或选候选；不得调用推演和部署 |
| `unavailable` | `null` | 可操作的失败说明 | 保存输入草稿、手动修正或显式重试；不伪造路线继续 |

失败与待补充时可以保存“输入草稿”，但不能把它标为“可执行计划”。错误响应不是正常结果加一行警告。兼容旧客户端时仍返回可理解的 `questions`；新 `state`、`reason_code` 等字段须有双端测试和已确认示例。

### 5.2 本地标签的最小 JSON 示例（提案）

```json
{
  "id": "label_work",
  "title": "日常工作",
  "color": "#355CDE",
  "description": "办公室及日常办事地点"
}
```

记录标题、颜色和描述；允许用户编辑，显示名称不参与算法逻辑。地点另存稳定标识和标签引用，不在每个计划节点重复复制标签内容。

### 5.3 时间快照示例（内部提案）

```json
{
  "now": "2026-11-28T20:00:00+08:00",
  "timezone": "Asia/Shanghai",
  "source": "server",
  "checked_at": "2026-11-28T20:00:00+08:00"
}
```

该快照描述一次取时结果，不声称已通过 NTP 直接校准。往返耗时、偏差和重试状态属于取时模块内部；业务调用方使用快照，不处理网络协议细节。示例时间为说明用合成值。

## 6. 接口“可靠”的验收层级

| 优先级 | 检查层级 | 必须覆盖 |
|---|---|---|
| P0 | 语法与结构 | 非 JSON、截断、多余字段、错误类型、未知枚举、单位不符 |
| P0 | 语义 | 周边界、跨月跨年、闰日、跨午夜、次日参照、过去时间、到达/开始/出发区分 |
| P0 | 图与数据 | ID 唯一、引用存在、路径相连、无环、方式匹配、坐标范围与坐标系、未知 ETA 不冒充零 |
| P0 | 来源与时效 | 真实/默认/用户/演示来源准确；外部失败不是晴天或零耗时；过期路线不冒充新路线 |
| P0 | 失败与调用预算 | 整体超时和有限重试；SDK 隐式重试计入预算；缺字段时不调用昂贵接口；parse 不调用 POI 搜索 |
| P0 | 状态与一致性 | 待补充不能推演、旧版本不能覆盖新版本、同一刷新不重复叠加影响 |
| P0 | 端到端契约 | 真实 parse 流程产生的计划能直接传给同一引擎，失败结果能被当前甲端读取 |
| P1 | 交互与缓存 | 引导可重开、只补缺失信息、权限拒绝可手填、草稿恢复、跨午夜提示、字体/键盘/辅助功能 |

现有 7 个 LLM 客户端试点测试只覆盖其中一小部分。正式修复前要确定上述外部行为，再审阅测试。不能靠广泛捕获所有异常把程序缺陷包装成“上游失败”。

## 7. 推进边界
