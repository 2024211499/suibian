# 随变从零开发与逐步验收手册

这份手册交给两名开发者。甲负责 Android、手机系统动作和发布包，乙负责服务端、外部数据和计划引擎。每步由另一人用本节的输入重跑，记录实测值。以下文件名相对于 `suibian` 仓库根目录。示例用 Windows PowerShell，并假设仓库克隆到 `D:\dev\suibian`。

**交付分两次。** 初赛交付可安装的 Android Demo、可重建源码、可访问的服务、匿名计划书和实际运行视频。Demo 要在同一条杭州行程上完成生成、部署、应变和复盘。完整成品再补齐全部 25 项 P0 的可重复使用能力，以及定位语里「消息和同行人主动带来变化」的实际入口。成品验收要求另一位用户从空数据创建自己的计划，锁屏后收到提醒，改一次行程，次日还能打开记录并复用画像。产品范围沿用一城一天，跨城车次可作为用户导入的固定到达或返程约束。

## 开工前先对齐工程现状

工程已有 [服务入口](../server/app/main.py)、[接口骨架](../server/app/api/routes.py)、[数据模型](../server/app/engine/models.py)、[推演函数](../server/app/engine/simulate.py)、[画像函数](../server/app/engine/profile.py)、[方案搜索入口](../server/app/engine/search.py)和[数据契约](../schema/plan_graph.schema.json)。从第 00 步盘点并复用已有模块。目录、示例和测试中的 TODO 都需要结合实际执行结果判断。

| 两端需要一致的决定 | 本项目采用的约定 |
|---|---|
| 接口入口 | 健康检查用 `/v1/health`。生成先返回 `job_id`，手机订阅 `/events`，断线后按同一任务号取结果。环境检查和变化报告分别走 `/refresh`、`/tick` 和 `/report`，最终都调用 `/replan` |
| 计划字段 | 沿用 `version`、`edges`、`city_adcode`、`sim.p_all`。计划临时计算需要的 `depart_at`、`progress`、`context_snapshot` 放在请求外层。已有计划缺少出发时刻时要求补齐，禁止隐式按午夜计算 |
| 概率和画像 | 默认 `p_target=0.9`，读取每份计划的实际值。沿用 NumPy 路段对数正态推演、最终候选 2,000 次采样和仓库的正态共轭画像更新。解释、时间和概率来自同一份计算结果 |
| 可演示与可交付 | `MOCK=1` 用固定响应走界面。开发另接可替换的外部数据提供器，`replay` 只回放地图、天气、模型解析和事件输入，`live` 使用在线输入。这两种均执行真实引擎。正式试用默认 `live`，回放入口显眼标记数据来源 |
| 范围与优先级 | 初赛优先把第 00–12 步跑完。第 13–15 步交付完整成品。此前文档里的同步生成响应、1,024 次采样和 1.047 画像样例，在这个工程中统一使用本表的仓库约定 |

## 路线和审核方式

| 步骤 | 最早可并行的工作 | 交接物 |
|---|---|---|
| 00–02 环境、连通、契约 | 甲起 Android，乙起 FastAPI，并行到共用样例 | 真机能请求本机服务，测试能读同一张计划图 |
| 03–05 引擎、网关、生成 | 乙做计算，甲根据样例做录入和对比页 | 用户说一句需求，得到确实不同的可行方案 |
| 06–07 本地状态和部署 | 甲可从 02 开始，乙提供固定时长夹具 | 日历、提醒、待订清单都有可核对的结果 |
| 08–09 变化感知和重排 | 乙做重算，甲做确认、恢复和撤销 | 一个事件改变两个以上后续时刻，用户能采纳或保留原计划 |
| 10 复盘 | 甲做观测和本地画像，乙接入生成与重算 | 相同输入、不同画像得出可解释的结果差异 |
| 11–12 验证、部署、录制 | 两人互测，甲管 APK，乙管服务和结果 | 一套实际运行过的发布材料，能在另一台设备复现 |
| 13–15 完整成品 | 先补输入与后台，再接多人和消息，再做升级回归 | 普通用户能持续使用、授权、退出和升级 |

审核记录每项写一行 `步骤｜代码版本｜设备/系统或 Python 版本｜输入及来源｜预期｜实际｜通过/待修｜证据位置｜复核人`。出现错误时保存最小输入，补失败测试，修正后重跑该项及其上下游用例。固定响应截图只验界面；算法须有输入和计算输出；系统动作须有操作前后的真机证据。核验开发动作无需把用户的日历、姓名或消息写进共享日志。

## 02 冻结数据契约和金样例

**前置**　00，和 01 可并行。**负责人**　乙起草、甲用 Kotlin 反序列化。**产物**　API 契约测试、能贯穿四阶段的杭州样例、预期结果表。

以 `schema/*.schema.json`、`server/app/engine/models.py` 为共享数据依据。Android 用 `@SerialName("from")` 等 映射保留 JSON 原名，Python 出站 `model_dump(by_alias=True, exclude_none=True)` 并用 JSON Schema 验证；允许明确为 null 的字段按接口契约处理。仓库当前 Schema 对未声明字段会拒收。按仓库协作约定，共享 Schema、动作表和配置示例由两人核对后由团队维护；优先给请求建外层模型，避免移动现存字段。

| 对象 | 约定 | 审核用的反例 |
|---|---|---|
| `PlanGraph` | `plan_id` 是稳定 ID，`version` 是内容版本，`date` 是计划当地日期，`nodes[].id`、`edges[].id` 唯一。首版一条有序链，活动用 `nodes`，路段用 `edges` | 重复 ID、悬空边、环、分叉、负时长、`25:90` 应在进入计算前得到带字段位置的 422 |
| 约束 | 预约最晚开始由节点 `hard + window.latest` 表达；返程最晚到达用 `constraints[].type=arrive_by` 表达。所有硬条件逐项给结果。硬预算只在费用完整时可验，缺费用返回待确认 | 不能删除必去展览；未知营业时间标待核实；无法支持的硬条件不能静默消失 |
| `RunContext`（新增请求模型） | `depart_at` 含日期和时区，`now` 是观察时刻，`progress={anchor_id,anchor_at,completed_ids}`，`seed` 固定可复现；`source_mode` 由服务运行配置决定 | 同一输入刷新两次无随机跳变；把锚点设在不存在的路段得到错误 |
| `ContextEvent`（新增） | `event_id, kind, starts_at, ends_at, affected_ids, data, source, fetched_at`。同一来源的同一预报时段和内容生成稳定 ID | 把同一场雨重复提交两次，总延误不叠加；较旧预报不能覆盖较新预报 |
| `Option` 与 `SimResult` | 每个候选含完整可校验的 `plan_after`、`sim`、修改项、损失和依据。API 输出统一 `per_node` 为对象数组，每项含 `node,p_ok,arrive_p90,slack_p50`，适配引擎内部字典。分钟内部计算，UI 层格式化时间 | 简写的 `{plan_id}` 可以画假卡，不能作为可部署候选；JSON 不出现 NaN/Infinity |

**共同样例的输入。** 周六三人在杭州，从龙翔桥出发，湖边散步、吃午饭，14:00 入场看展，18:00 前返回。创建 `eval/datasets/replay/hz_rain_01.json`，标 `source: synthetic`。相邻路段、可替代路段、室内备选、营业窗、天气窗各带来源。当天 12:10 已到湖边，把此前的行程固定。下表所有时间和耗时均为人工验算输入。午饭可提前，展览最早和最晚开始均为 14:00，观展 60 分钟，返程 25 分钟。

| 情况 | 从锚点起累计分钟 | 预计到展馆 | 硬条件 |
|---|---|---|---|
| 原计划 | 湖边 25 + 去午饭 10 + 午饭 45 + 去展馆 20 = 100 | 13:50 | 等到 14:00 入场，15:25 返回，通过 |
| 降雨扰动 | 原路径多等 20 分钟，共 120 | 14:10 | 错过入场，必须指出展览受影响 |
| 方案 A | 湖边缩短至 10 分钟，仍需避雨 20 分钟，共 105 | 13:55 | 保留短暂湖边体验，通过 |
| 方案 B | 直接去午饭点 15 + 午饭 45 + 去展馆 20 = 80 | 13:30 | 放弃湖边活动，通过 |

**审核**　乙把四行变成确定性断言，甲在同一份 JSON 上显示同一组字段。用这份样例验算时间传播；另带一份已核验的 POI、真实路线和天气快照测网关。两人更换输入中的 20 分钟为 30 分钟，受雨路径的到展馆时刻应再晚 10 分钟，直达备选不受影响。

## 03 做可独立审查的推演引擎

**前置**　02。**负责人**　乙开发，甲用金样例复算。**产物**　`engine/simulate.py`、输入校验、`POST /v1/simulate` 的真实实现与回归测试。

1. 先写无随机性的引擎。按边建立入度和邻接关系，在首版链上从唯一原点走到终点。行中从锚点的实际时刻向后推进。`arrive=上段结束+路段耗时`，`start=max(arrive, earliest)`，`finish=start+stay`。营业窗有明确闭店时刻时检查整个停留区间。独立 `arrive_by` 检查目标节点的 `arrive`，硬预约检查 `start`。无截止时缓冲返回 `null`。
2. 快速补两个实测回归。① 12:00 出发、步行 20 分钟、独立硬约束 12:15 前到，确定性 `p_all` 应为 0；当前 v0 可返回 1。② 出发搜索上界本身可行时必须返回上界，v0 的二分会少 1 分钟。覆盖最早也不可行、两端相等、节点乱序、遗漏时间和环。明确支持的最长行程，跨日统一用有日期的时刻或返回待拆分。
3. 加随机时长。路段 `eta × 画像系数 × 天气系数 × exp(σz−σ²/2)`；停留时长按已有均值和方差采样并截断在零以上。核实公交 ETA 是否已经包含等车时间，按来源只加一次。不同候选对未变路段使用按路段 ID、抽样类型和 seed 派生的稳定随机流。每个样本逐项与硬条件相交，`p_all=全部满足的样本数/总数`。选最薄弱的有截止硬节点，概率相同再比时间缓冲。
4. 输入 `p_target`，在允许出发区间内找最晚可行时刻。固定 ETA、固定扰动且成功率单调时可二分，先测上下界；采用分时公交、开放时段或随时刻变化的风险后，以明确的一分钟格点或公布的时间粒度枚举复算。显示 `remind_at=depart_by−prep_min`，无可行时刻应给原因。
5. 路由层按输入调用算法，返回 `sim` 和 `evidence`；在演示模式给来源标签。纯函数里禁用网络，2,000 样本、20 节点测实际机器 p50/p95 并记录环境。先查复杂度再调整抽样数，并保存 `seed,n_samples`。

**审核**　四个到达时间逐项相等；同输入和 seed 两次结果一致；提前硬截止不会提高把握；0 和 1 都能通过确定性案例测出来。甲改变一个截止时刻，通过 HTTP 看到响应随之变化。单个接口仍只返回 `schema/examples` 时，记录为界面联调通过、引擎接线待验。

## 04 接百炼、高德、和风，保留可复现输入

**前置**　02。**负责人**　乙，甲核对显示字段。**产物**　三套可换实现、脱敏样本、独立的外部服务冒烟测试。

1. 在开发者控制台创建服务端凭据。项目设置已读取 `QWEN_BASE/QWEN_MAIN/QWEN_KEY`、`AMAP_WEB_KEY`、`QW_HOST/QW_PROJECT_ID/QW_KEY_ID/QW_PRIVATE_KEY`。从 `server/` 启动时写入该机的 `server/.env` 或 `deploy/.env`。先验证一个模型，再按需启用现有主备客户端。免费额度、模型 ID 和天气域名取各自账号的实际值，记录日期和单位。仓库与 APK 只保留变量名。
2. `app/llm/client.py` 只做结构化抽取。输入含当地日期、匿名原话和可选确认字段。输出先过 `intent.schema.json` / `skeleton.schema.json` 校验，再核验日期、返程时刻、偏好与必做项。保留用户原话中明确提供的数字，缺关键字段放 `questions[]`。仅重试一次校验失败或暂时性错误，超时走可编辑表单。`redact.py` 在请求出端或进入服务前按字段最小化，`render.py` 仅填已知占位符。[百炼结构化输出](https://help.aliyun.com/zh/model-studio/qwen-structured-output)
3. `app/gateway/amap.py` 先实现 `search_text`、`poi_detail`、`route`，输出内部 `Place/LegQuote`。校验 API 业务状态，读取 POI ID、名称、经纬度、可核实的营业信息。步行和公交分别走对应的 v5 规划接口；地理坐标按高德约定传经度在前，公交带起终点城市参数。统一把秒转分钟、米保留为米。查询时间、出行时段、来源随报价返回。目的地不同要分别查询，当前驾车 ETA 的变化只解释相应交通方式。售票、临时闭馆和预约名额若无来源，页面标待核实。[高德路线文档](https://lbs.amap.com/api/webservice/guide/api/newroute)
4. `app/gateway/qweather.py` 依据账号实际 API Host 和已开通的小时预报接口做一次调用，使用项目 ID、密钥 ID 和 Ed25519 私钥签发短期 JWT。按正在使用的接口规定处理坐标系、经纬度精度和顺序，读取预报时间、降水量/概率、天气现象和更新时间，映射成 `HourlyForecast`。统一为带时区的时刻。示例旧路径仅在该账号实际支持时启用；天气和路况分别处理失败。[和风小时天气](https://dev.qweather.com/docs/api/weather/weather-hourly-forecast/) · [和风鉴权](https://dev.qweather.com/docs/configuration/authentication/)
5. 给每个外部函数注入 `LiveProvider` 或 `ReplayProvider`。回放键由规范化请求和时段生成；找不到该输入时返回 `missing_data`。缓存键带交通方式和时间桶，保留 `fetched_at/valid_until`；缓存过期标陈旧。按账号配额配置并发、每日调用上限和退避，记录请求数、耗时、缓存命中和业务错误码，避免把 URL 中的 key 写进日志。写入 `eval/fixtures/` 的原始响应先去除个人和凭据字段。

## 10 复盘并影响下一次生成

**前置**　03、05、06。**负责人**　甲做本地 `BayesUpdater` 和复盘页，乙对照 Python。**产物**　可更正、可暂停、可删除的观测记录和可验证的个性化。

1. 从「出发了／到了」获得同一条路段的起止时刻，或让用户在复盘页填写实际分钟。同时保存当时的**原始地图 ETA**、方式、时段。拒绝非正数，特别大的偏差询问是否中途办事。修订同一记录沿用 `observation_id`，避免重复计数。按步行等方式和高峰/非高峰分组，先打通步行一组，再加入准备时间和其他方式。
2. 按 `server/app/engine/profile.py`，令 `r=ln(actual/eta)`。对该分组最近 30 条有效记录，用 `μ₀=0, τ₀=0.2, σ=0.15`，计算 `v=1/(1/τ₀²+n/σ²)`，`μ=v×(μ₀/τ₀²+Σr/σ²)`，`τ=√v`，`factor=exp(μ)`。空组系数 1。首条 20 分钟预计、24 分钟实际，系数约 **1.123766**，下次相同 20 分钟步行段的均值约 **22.48 分钟**。准备时间以实际分钟和默认分钟之差单独更新。
3. 复盘页面展示计划/实际、偏差、样本数，用户可排除、改写、删除、暂停。下一次生成及重排都带版本化画像，服务端只乘一次系数。对照实验固定路线、天气和 seed，仅替换画像；若出发建议受整分舍入未变，展示预计步行分钟的真实差异。

**审核**　两端读取同一份 `schema/testvectors/profile.json`；重交同一观测 `n` 不增，删除后可回到先验，暂停期间不新增学习样本。满 30 条的 `τ` 按常数计算约 `0.0271329379`，若本地向量仍写 `0.027134`，由维护人独立复核再修正测试数据，保留合理精度和共同容差。关掉网络也能查看和维护画像。
